> 2026-10-17。老板发来一个抖音视频（AI 产品千媚），讲的是社区对 Claude Code 运行逻辑的逆向分析。

## 一、Claude Code 的多 Agent 协同模型（社区逆向 + 官方文档）

一句话：**一个主 Agent 负责想办法和收口，子 Agent 是被主 Agent 按需拉起的「独立上下文工人」，只交回最终报告。**

| 机制 | 做法 | 为什么有效 |
|---|---|---|
| 主循环（orchestrator） | 单个主 Agent 跑「模型 → 工具调用 → 结果 → 再决策」的异步循环 | 所有决策集中，避免多个 Agent 互相抢方向 |
| 子 Agent（Task/Agent 工具） | 主 Agent 调工具生成子 Agent；子 Agent 有**独立上下文窗口**、独立工具权限、独立模型；默认不能无限再生成子 Agent | 上下文隔离：探索/搜索/读大文件的噪声留在子 Agent 里，主上下文只收结论 |
| 结果契约 | 子 Agent 只返回**最终报告**（不是完整过程），主 Agent 把它当一条工具结果 | 主上下文不被过程撑爆；成本可控 |
| 专用 Agent 类型 | 通用型、Explore/Plan 等专用型；用户可在 `.claude/agents` 定义角色（描述、可用工具、模型） | 角色化：便宜模型做侦察，贵模型做关键决策 |
| 并行 | 主 Agent 可同时发起多个子 Agent；独立的活并行，有依赖的串行 | 时间缩短，且主 Agent 保持可响应 |
| 计划/待办 | 计划模式、TODO 列表贯穿；先探索再计划再执行再验证 | 长任务有「锚点」，不会边做边丢目标 |
| 上下文管理 | 自动压缩/摘要、工具输出截断、文件按段读取、搜索优先于整读 | 长会话可持续，成本可控 |
| 权限与围栏 | 权限模式、允许列表、hooks（工具前后）、沙箱、人工审批 | 子 Agent 能干活但不越权；破坏性操作要人批 |
| 验证 | 计划→执行→测试/校验→再修；失败重试有上限 | 「做完了」不等于「做对了」 |

## 二、一念已经有的（对照表）

| Claude Code 的机制 | 一念对应物 | 差距 |
|---|---|---|
| 主 Agent | 总控 / 部门负责人 `submit_plan` | ✅ 有；但总控同时管公司层，需要更清晰「总控=总统筹」 |
| 子 Agent | 派单 run / 子任务，独立任务会话 | ✅ 有，且比它多：部门、编制、预算、验收人 |
| 独立上下文 | 每个子任务独立对话线程 | ✅ 有；子任务结果只回传给总控汇总（已裁剪长度） |
| 结果契约 | 子任务 result；已有 `acceptance/boundaries/deliverable/reviewer` | ⚠️ 结果还是自由文本；Handoff 结构化字段已设计未强制 |
| 专用 Agent 类型 | 推荐模型 + 自动建专员 | ⚠️ 缺「角色模板库」（角色=工具权限+提示词+默认模型） |
| 并行 | 依赖就绪即并行、并发上限 | ✅ 有 |
| 计划/TODO | 派单计划 + 子任务状态 + 复盘记录 | ✅ 有；长任务 State Doc 已设计 |
| 上下文管理 | 子任务 brief 自包含、结果裁剪、记忆预算 | ⚠️ 缺「总控侧」的自动摘要/装配器（长任务设计里有） |
| 权限围栏 | 公司层规则、预算、审批、autoApprove | ⚠️ 目前派单员工 autoApprove 一刀切；缺**按角色**的只读/可写权限 |
| 验证 | 验收标准 + 验收人字段 | ⚠️ 只有字段，没有闸门（计划中的阶段 2） |

## 三、最值得吸收的 5 件事（结合一念特色）

1. **角色模板库（Agent Library）**：把「研究员/设计师/验收员/写手」做成模板：描述、可用工具、只读/可写、默认模型、提示词骨架、验收要点。派单匹配时按模板找人/建人，而不是每次靠模型即兴发挥。
2. **按角色的工具权限**：侦察/调研类只能读、搜索、看资料库；实现类才能写文件/跑命令；对外发布永远要人批。比现在「派单员工全 autoApprove」更安全、也更符合「一 Bot 一任务」的权限边界。
3. **强制 Handoff 契约**：子任务结束必须交固定字段（done/evidence/decisions/openQuestions/nextStep/acceptance），主 Agent 汇总只读 Handoff，不回读全文——省 token、可审计。
4. **总控的上下文纪律**：总控上下文 = 任务宪法 + State Doc + 各子任务 Handoff 摘要（上限）+ 最近消息；**不重放**子任务原文；这同时解决「长任务不丢方向」和「换模型交接」。
5. **验证闸门（Verification Gate）**：子任务交付后先按 acceptance 由 reviewer（Bot 或人）判 pass/fail；不过就退回重做/换模型。Claude Code 用测试/校验做闸门，我们用验收标准 + 验收人做闸门，这是我们的差异化。

## 四、不建议照搬的

- 不照搬「单主 Agent 一把抓」：一念是公司层（总控 → 部门 → 员工），要保留组织与预算、编制、隔离。
- 不照搬「子 Agent 无限自我繁殖」：保留 `MAX_COMMS_DEPTH` 递归上限，防止失控与成本爆炸。
- 不照搬「结果自由文本」：我们的验收/边界/交付物字段比它更结构化，应该加强而不是退回。
- 不照搬它的工具名/UI：只学机制。

## 五、给 1.1.4 / 1.1.5 的落地顺序

| 优先级 | 改动 | 依赖 |
|---|---|---|
| P0 | 角色模板库（数据 + 设置页可编辑 + 派单匹配使用） | 现有推荐器 |
| P0 | 按角色工具权限（只读/读写/命令/发布），派单员工按模板继承；发布永远人批 | 公司层规则 |
| P1 | 强制 Handoff 契约 + 汇总只读 Handoff（省 token、可审计） | 派单结果结构 |
| P1 | 验证闸门：reviewer 按 acceptance 判定，不通过退回/重试 | Handoff + 验收字段 |
| P2 | 总控上下文装配器（宪法 + State Doc + Handoff 摘要 + 最近消息，带预算与注入清单） | 长任务阶段 D |
| P2 | 任务文件夹 UI + 任务负责人权限（1.1.4 已开始） | 任务数据层（已完成） |
