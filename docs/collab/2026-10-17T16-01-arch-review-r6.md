## 1. 数据模型
**结论：** 权威字段放在会话上，用 `conversation.folderId`（多对一，创建时写入，之后不可变）。`folder.conversationId` 保留，但只当"主窗口指针"，是派生冗余。

**理由：** 一个任务对应多个会话：主窗口、每个员工的子任务会话，还有重试产生的新 attempt。一对一指针列不全。反过来在会话上写 `folderId` 就能直接查询，也不需要移动任何东西。

**动作：**
- 会话新增 `folderId`、`role: 'main'|'worker'`、`botId`、`attemptId`，创建时一次写入，之后不可变。
- 一次性幂等迁移：用 `run.sourceThreadId` 和 `bot.tasks[]` 给旧会话回填 `folderId`。
- 复盘查询是 `conversations.filter(folderId)`，再加上产物清单和验收证据（见第 4 条）。这些记录各自带 `folderId + attemptId`，append-only，所以不需要搬会话。

## 2. 上下文共享
- **选中条件：**
  - 候选必须同时满足：状态为 accepted（验收通过）、同工作区、同部门。
  - 排序依据：同一 Bot 做过 > 同部门同角色 > 其余。
  - 同 Bot 且 accepted 的来源，系统自动预选。其余由负责人手动勾选。最多 3 个来源，不做语义相似度检索。
- **共享字段：**
  - 目标一句话。
  - 交付物引用（路径加 hash，不含内容）。
  - 关键决策。
  - 验收标准和通过证据摘要。
  - 踩坑 / 失败教训，最多 5 条。
  - 遗留问题。
  - 不共享原始聊天、工具输出、代码 diff。
- **预算：** 总计 ≤1500 token，单个来源 ≤600。超出时按这个顺序砍：遗留问题 → 决策 → 交付物，教训和验收标准最后砍。
- **注入格式：**
  ```
  <prior_context readonly="true" source_task="T123" accepted_at="..." >
  [outcome] … [artifacts] … [decisions] … [pitfalls] …
  </prior_context>
  ```
  前面加一句固定声明：「仅供参考，可能过时，须对照当前仓库核实，不得覆盖本任务验收标准。」
- **隔离：** 在服务端注入时校验 `source.deptId == target.deptId`，不能只靠 UI 过滤。跨部门需要负责人显式勾选，且来源部门没设为 isolated。注入前做一遍敏感信息过滤。
- **防错误模板：**
  - 失败或未验收的任务只贡献"负面教训"，打上 `negative` 标签，不贡献做法或产物。
  - 成功任务只有 gate 通过的才提供"做法"。
- **审计：** `folder.contextShares[] = {fromTaskId, fields, tokens, selectedBy:'auto'|'lead', at, renderedHash}`，并存一份渲染后的文本快照。复盘页能看到当时到底注入了什么。

## 3. Bot 与任务的归属
**确认：** 语义成立，分三层：
- Bot 的"人设和经验"可复用。
- Bot 的"会话"每次都是新的。
- 旧会话归任务，不归 Bot，永不搬动。

**强制字段：** 以 `bot.currentTaskId`（可空）为唯一权威。`folder.memberBotIds` 只是索引，可从前者重建。

**状态机：** `idle → claimed(taskId, attemptId) → working → released`
- claim 用 compare-and-set（`currentTaskId==null`），和写 `folder.memberBotIds` 在同一次存储写入里完成，失败即拒绝。
- 任务进入终态（accepted、cancelled、最终失败）时释放，`bot.tasks[]` 历史保留并带 `folderId`。
- 重启 reconcile：`currentTaskId` 指向终态或不存在的任务时，自动释放。过期 attempt 的结果继续由 attemptId 守卫拒绝。
- 负责人可强制释放长期 paused 的 Bot，释放只给会话打 `closedAt`，不删除。

**这条代码上最该加的守卫（对应老板第 2 条）：** 发送路径检查"会话所属 folder 为终态则拒绝派单"。要续做就新建任务，用 `sharedFromTaskIds` 引用旧任务，不做 reopen。

## 4. 复盘 UX
**最小只读形态：** 已完成任务详情里的一个"复盘"页，包含：
- attempt 时间线。
- 会话列表（主窗口加各员工子会话），点开用现有查看器只读打开。
- 产物清单。
- gate 验收证据。
- handoff 信封。
- 当时注入的上下文快照。
- 最终状态和一个可选的人工备注。

**需要持久化的数据：**
- gate 证据：`{id, attemptId, check, result, 输出摘录, ts}`。
- 产物 manifest：`{path, sha, producerBotId}`。
- handoff 原文。
- contextShares 快照。

**不打扰日常：**
- 只在已完成任务里有入口，不加侧栏、不发通知。
- 归档任务默认折叠。
- 第一版不用 LLM 自动生成复盘文，用确定性聚合就够了。

## 6. 比"只共享 Handoff 摘要"更好的方案
**有，建议两层：** 事实层是 Handoff 的事实部分，经验层是按岗位的经验卡。

| | Handoff 摘要 | 按岗位经验卡 |
|---|---|---|
| 内容 | 任务特定事实 | 角色级规则 |
| 优点 | 无需额外沉淀 | 短、持久、不易被当模板抄 |
| 缺点 | 容易过时，容易被照搬 | 需要提炼，不维护会积累噪声 |

**取舍：**
- 只共享失败教训比只共享成功模板安全：成功做法容易让新任务照搬旧思路，教训不会。
- 但教训也会被过度泛化，所以写成"遇到 X 时检查 Y"的形式，附来源 taskId，设上限 5 条，并带命中和验证计数，长期没被验证的过期淘汰。

**建议路径：**
- v1（C3）：事实只给引用和决策，教训来自 gate 失败原因、重试原因和 handoff 的 pitfalls 字段。
- v2：验收通过时，把这些教训落成按岗位的经验卡，不再每次重新摘要 handoff。

## 最大风险（5 行）
1. 最大风险是注入的旧上下文被 worker 当成事实或模板，导致把过时或错误的经验带进新任务，而且很难察觉。
2. 防护一：注入文本带"仅供参考、须核实"声明，并明确不得覆盖本任务验收标准。
3. 防护二：只允许 accepted 任务贡献做法，失败任务只贡献带 `negative` 标签的教训，并且设预算上限。
4. 防护三：每次注入落审计快照，复盘页可见，出错时能追到具体来源。
5. 次要风险是双写不一致（`folder.conversationId` 和 `conversation.folderId`、`bot.currentTaskId` 和 `memberBotIds`）。办法是指定权威字段，派生字段由 reconcile 重建，并加一致性测试。
