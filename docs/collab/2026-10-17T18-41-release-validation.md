## 2) 长任务实测协议

**怎么跑**
1. 开跑前备份数据目录快照，记录各 JSON 的 sha256 作为 baseline。
2. 在一次性项目上跑，不碰真实重要数据。先跑 30 到 60 分钟的中等任务，稳了再放长。
3. 全程固定一个 run 标记：在已有 transcript 里写一行 `run-start` 和一行 `run-end` 即可，不加新埋点。
4. 进化开关保持关闭，成本上限设低（比如预期的 1.5 倍）。

**6 个指标**
1. 验收一次通过率和最终完成率。
2. 老板介入次数和 owner-time 分钟数，用已有的 owner-time 接口。
3. 累计成本占上限的百分比。
4. attempt 数分布，重点看 ≥3 次的任务和超时数。
5. 距最后一次有效产出的时间，反映卡死。
6. 一致性差异数：收件箱 vs 顶栏，SSE vs 轮询。正常应恒为 0。

**立刻停止或回滚的条件**
- 成本达到上限 100%（80% 预警）。
- 同一任务 attempt ≥ 3。
- 超过 15 分钟无产出。
- 一致性差异 ≥ 1 且持续超过 1 分钟。
- 任何 JSON 解析失败。
- 出现未经确认的写操作（进化、改配置）。
- 内存或 CPU 持续异常增长。

**回滚步骤**：停服务→还原快照→装回 1.1.3→确认进化开关为 off。

**提前埋的数据**：只需要上面的快照、baseline 哈希和 run-start/end 两行标记。现有的 attempt、成本、owner-time 事件已经够用，不要为此新增埋点。

## 3) 架构风险 Top 5

1. **attempt 幂等与 ack sweep 竞态**
   - 后果：重复执行、成本翻倍，状态可能从终态回退。
   - 触发：重启后 sweep 立刻跑，同时有迟到的隐式接收。
   - 缓解：`attempt_id` 由 task、handoff、seq 确定性生成。状态转移用“期望旧状态”做 CAS，终态不可回退。sweep 在写入前重新检查 `state==pending && deadline<now`。

2. **双「需要你」口径**
   - 后果：红点、此刻条、晨报数字对不上，老板对系统失去信任。
   - 触发：收件箱（按人）和注意力闸门（按决策）各自计数。
   - 缓解：只保留一个 `selectNeedsOwner()`，所有 UI 和晨报都调用它。加一个契约测试比对三处输出。

3. **SSE 与轮询不一致**
   - 后果：UI 闪烁，旧状态覆盖新状态，断线期间事件丢失。
   - 触发：重连、事件乱序、轮询慢于 SSE。
   - 缓解：所有状态带单调递增的 `revision`，客户端丢弃 revision 更小的数据。重连后先全量拉一次再接事件。轮询只做兜底。

4. **JSON 文件存储并发**
   - 后果：丢更新，或写到一半文件损坏。
   - 触发：dispatch、sweep、SSE 触发的处理、进化同时读改写同一文件。
   - 缓解：每个文件在进程内走单写队列（promise mutex），用 tmp+rename 原子写。启动时校验，失败就回退 `.bak`。禁止多进程写同一文件。

5. **上下文注入安全**
   - 后果：不可信文本变成另一个任务的指令，或跨项目泄露。
   - 触发：fork 或共享注入了工具输出、网页内容、其他任务的原文。
   - 缓解：注入块放在显式分隔且标注 `untrusted` 的数据区，不进指令位。按项目做 allowlist，设长度上限，剔除密钥类字段。只记录注入的来源和 hash，不记全文。

## 4) 隐私、安全与成本

**必须脱敏或不落盘**
- **自我进化读复盘**：不落盘复盘原文，只存摘要、指标和引用 ID。读入前先脱敏：
  - API key 和 token（包括 URL query 里的）
  - 邮箱
  - 含用户名的绝对路径（如 `/Users/kairuiwang`）
  - 环境变量
  - 外部人名和客户名
  - 原始文件内容
- **上下文共享**：只传引用 ID 加摘要。合并后的完整 prompt 不落盘。严格按项目边界过滤。
- **项目 office**：owner-time 只存聚合值（分钟/日）。日志里任务标题要截断。不记录 owner 的逐条行为轨迹。

**成本上限**
- **位置**：硬上限放在服务端 dispatch 入口，派发前检查，分三层：单 attempt、单任务、全局每日。不要只靠 UI 限制。
- **UI 可见性**：顶栏常驻“今日 $x / 上限 $y”，80% 变黄，100% 变红并停止新派发。每个任务卡显示累计成本。触发上限时往「需要你」推一条，要去重。

## 5) 30 秒晨报的 5 个数字

1. 昨夜完成任务数，以及验收一次通过率。
2. 「需要你」待处理数（唯一口径），以及最老一条已等待多久。
3. 昨日 owner-time 分钟数。
4. 昨日成本和占上限的百分比。
5. 异常数：失败、超时、重试、sweep 触发之和。

## 6) 只留一个发布前必修的 bug

Handoff ack 超时 sweep 与 dispatch 隐式接收的竞态，会产生重复 attempt。原因：这是今晚唯一把时间驱动的写操作接进主调度的地方，出错会直接重复执行并多烧钱，而且纯逻辑单测很难发现。
