# 项目内 AI 协同办公工作台（Project Office）规格

> 状态：设计定稿，待老板拍板 2 个取舍（是否做桌面三栏、Handoff ack 是否本版落地）。
> 日期：2026-10-18
> 范围更正：这里的「工作台」是**打开一个项目后，老板看到的 AI 团队如何协同办公**，不是 app 首页 / 侧栏 / 决策栈。
> 依据：`docs/collab/2026-10-17T17-43-project-office.md`（Claude 最新设计）、`docs/collab/2026-10-18-session-summary.md`（任务窗口 / dispatch / Handoff / 收件箱 / retro / StateDoc 现状）、`docs/task-centric-workbench.md`。
> 术语：项目 = 现有任务文件夹（task folder）；负责人 = 项目总控 bot；老板只看到「谁在等谁、我欠不欠一个决定、项目到哪了」，对话是下钻层，不是主屏。

## 1. 项目运营模式

### 1.1 角色与权利边界

| 角色 | 能做 | 不能做 |
|---|---|---|
| 老板 | 改目标/范围、拍板、点名追问、打回、终止项目 | ——（默认不被打扰，只收 5 类拍板点） |
| 项目负责人（总控 bot，每项目恰好 1 个） | 拆解、派单、调序、换人、汇总、升级给老板；推进部门间交接 | 评审自己拆出来或参与执行的产出；改目标；做对外/不可逆动作 |
| 部门（内容/设计/评审/研发…） | 认领本部门类型的子任务，部门内部分配、调整 | 越部门直接改别人的子任务；跳过交接直接开工 |
| 成员（执行 bot） | 执行、提交产出、发起交接、提出「受阻」 | 自评、改派、关闭自己的子任务、自己宣布完成 |
| 评审员 | 通过 / 打回（必须写理由和引用证据） | 修改被审产出；评审自己参与过的子任务 |

**项目负责人的三个硬约束**：
1. 负责人不能兼任本项目的评审员；它写过的子任务自动进 `authorIds`，永久失去评审资格。
2. 负责人只能在自治信封内换人/调序/重试（§1.5），越界必须生成拍板卡并停下。
3. 负责人不直接对老板说话之外的成员发号施令；对外/不可逆动作一律走老板拍板。

### 1.2 部门间交接：四件套 + 显式确认

部门之间不靠聊天交接，靠一张结构化交接单（Handoff）。

**交接必须包含四件（缺一件不能发送）**：
1. **产出物引用**：文件 / 链接 / 版本号，可直接打开；
2. **做了什么、没做什么**：一段事实清单，写明边界；
3. **验收标准**：接收方按这几条判断是否合格；
4. **未决问题**：还悬着的事、需要谁定。

**交接状态机**：`draft → sent → received → consumed`，旁路 `returned`（退回补件）、`expired`（超时升级）。

| 从 | 事件 | 到 | 谁 | 规则 |
|---|---|---|---|---|
| draft | 四件齐 + 发起 | sent | 产出方成员 | 缺件禁用「发送交接」；按钮旁写明缺哪件 |
| sent | 接收方点「接收」 | received | 接收方成员 | 写 `ackedAt`、`ackBy`；接收即进入对方工作队列 |
| sent | 接收方点「退回补件」+ 原因 | returned | 接收方成员 | 原因必填，回给发起方，交接物不消失 |
| returned | 发起方补齐重发 | sent | 产出方成员 | 保留上一轮记录，次数 +1 |
| sent | 超时（默认 30 分钟）无人接收 | expired | 系统 | 自动升级给项目负责人重派；**老板不会直接收到这类事** |

- 交接确认**必须显式**，系统不代签；「已读」不等于「接收」。
- 接收方开始工作后，交接物视为 `consumed`，后续返工走新的交接，不覆盖旧记录。
- 每次交接的接收/退回都进项目事件流，复盘可查。

### 1.3 评审不得自评：服务端硬校验

- 校验公式：`reviewerId ∉ 该子任务 authorIds[]`；`authorIds` 包含所有对产出写过内容的人，也包含改过内容的负责人。
- 优先跨部门评审；同部门评审必须在服务端留下理由，且下一轮自动换人。
- 校验失败返回 `REVIEWER_CONFLICT`，前端重新选评审员；**不是只在 UI 置灰**。
- 评审只出结论和证据（引用到具体段落/文件行），失败或证据不足转「需要你」，禁止模型自评当裁决。
- 项目级总验收：评审通过后仍可能生成老板拍板卡，是否免确认由项目自治等级决定（§1.5）。

### 1.4 老板只有 5 类拍板点

| # | 拍板点 | 触发条件（可落字段） | 默认动作 |
|---|---|---|---|
| 1 | 目标或范围变更 | 子任务新增/删除导致范围变化、目标字段被改 | 停下，生成卡 |
| 2 | 不可逆或对外动作 | 发布、发送、花钱、删除、对外承诺 | 停下，生成卡 |
| 3 | 同一子任务被打回 ≥2 次仍未过 | `reviewRound >= 2` 且未通过 | 停下，生成卡 + 异常 |
| 4 | 超出自治预算 | 时间 / 重试次数 / 成本超项目预算或回数上限 | 停下，生成卡 |
| 5 | 成员或部门冲突 | 负责人无法裁决（评审 vs 执行对立、跨部门抢件） | 停下，生成卡 |

其余全部走负责人自治；老板不接收「进度汇报式」打扰。卡片按钮固定：**「同意」「打回并说明」「稍后」**；打回必须写一句原因，这句原因回写成下一轮交接的验收标准补丁。

### 1.5 老板不在时：自治信封

负责人只能做信封内四件事：
1. 重派（换人或退回队列）；
2. 调序（优先级重排）；
3. 重试（同一子任务最多 2 次）；
4. 跳过非关键项（标 `skipped`，进复盘）。

越界即停：生成一张拍板卡，任务停在原地，**不硬跑、不代替老板批准**。老板回来先看到「你不在时」摘要：
`你不在时：完成 4 项，卡住 1 项，需要你 2 件。` 三个数字都可点开看原始事件。

## 2. 项目工作台主屏

### 2.1 信息层级（从上到下）

1. 项目标题 + 状态胶囊 + 一句话目标；
2. 进度条（`3/7 子任务 · 预计周五完成`）；
3. **需要你**（拍板卡，第一张展开，其余折叠「还有 N 件」）；
4. **此刻**（一行谁在等谁，可点开等待链）；
5. **团队**（按部门列成员 + 状态点 + 当前状态）；
6. **协作流**（谁 → 谁 · 交付物 · 状态 · 等了多久，点「全部」进协作 tab）；
7. **⚠ 异常**（被打回 ≥2 次、受阻超时等，带「看原因/换人/我来定」）；
8. 底部 tab（概览 / 协作 / 对话 / 复盘）+ 输入栏「对全队说… @点名」。

**排序原则**：先回答「要我干嘛」（拍板 + 异常），再回答「谁卡住了」（此刻 + 协作流），最后才是「项目叫什么」（标题 + 进度压成两行）。

**手机首屏只放四样**：状态胶囊 + 一句话目标、一张拍板卡 + 「还有 N 件」、此刻一行、底部输入栏。团队 / 协作流 / 异常下滑可见，或进「协作」tab。桌面端为三栏：左团队状态、中协作流（可展开等待图）、右拍板 + 对话。

### 2.3 各区块确切文案与按钮

**顶部**
- 项目名：`官网改版`
- 状态胶囊：`等你拍板` / `进行中` / `受阻` / `已完成` / `已暂停`
- 目标一行：`目标：{一句话目标}`
- 进度：`{done}/{total} 子任务 · 预计 {预计完成时间}`；无预估时 `{done}/{total} 子任务 · 预计时间待定`
- 右上「⋯」菜单：`调整目标` / `调整优先级` / `暂停项目` / `终止项目`（终止需二次确认：`终止后团队停止工作，产出都留着。确定终止「官网改版」？`）

**需要你**
- 区块标题：`需要你（2）`，数字随未处理卡数量变化。
- 卡片：一行问题式标题（`最终文案可以对外发布吗？`）+ 一行依据（`评审阿哲已通过 · 小林提交 · 含对外文案`）+ 2–3 行证据（`✓ 终稿已核对`）。
- 按钮：`同意`（主）、`打回并说明`（次）、`稍后`（次）。同意后卡片飞走、下一张补位；全部清空显示空态：`团队运转正常，没有需要你的事。`
- 折叠：`还有 N 件 ›`；点开切换下一张。
- 打回弹层：原因必选（`文案不对 / 风险太大 / 范围跑偏 / 我想改一下`）+ 一句原因（必填，`哪里不行？一句就行`），按钮 `取消 / 确认打回`；成功后提示 `已打回：范围跑偏。负责人会重排，改完再叫你。`
- 稍后：`已稍后。明早 8:00 和晨报一起出现，今晚不再提醒。`

**此刻**
- 一行：`{人} 写完{交付物} → 等 {人} {动作}（已 {N} 分钟）`；点开竖向等待链：
  - 已完成：`小林 · 提交「首版文案」 · 02:08 ✓`
  - 进行中/等待：`阿哲 · 评审中 · 已等 6 分钟`
  - 连带阻塞：`阿美 · 等文案定稿，才能做落地页 · 已等 2 小时 12 分`；超过 15 分钟标红并出 `催一下` 按钮。
  - 终点：`你 · 最终确认（未到）`
- 催一下：`已催 {人}：一条 @ 消息已发过去，30 分钟没回应会升级成异常。`
- 空态：`此刻没人互相等，团队在各自推进。`

**团队**
- 按部门分组，成员行固定格式：`头像/姓氏 + 状态点 + 姓名 + 状态词`。状态词固定五种：`工作中 / 等待 / 评审中 / 受阻 / 空闲`。
- 状态点颜色：工作中=绿、等待=黄（或琥珀）、评审中=紫、受阻=红、空闲=灰。
- 点头像或名字：弹半屏 `{名字} · {状态}`，显示「现在在做什么 / 等谁 / 今天完成 N 项」，按钮 `问 TA` / `看 TA 在做什么`。`问 TA` 打开输入栏并预填 `@{名字} `。
- 部门标题右侧可显示 `N 人`；无成员显示 `暂无成员`。
- 状态只能由子任务/交接/评审事实推导，**不允许 bot 自己写「我在忙」**（见 §5 红线）。

**协作流**
- 每行固定格式：`谁 → 谁 · 交付物 · 状态 · 等了多久`。
- 状态词：`等待评审 / 等待接收 / 进行中 / 已接收 / 被打回 / 已交付 / 受阻`。
- 超过 15 分钟的等待，`等了多久`标红。
- 点「全部 ›」进入协作 tab；点击单行进详情（交接四件套 / 等待链）。
- 手机折叠为最近 2 行 + `全部 ›`。

**异常**
- 标题：`⚠ 异常`；卡片一行说清：`「{子任务}」被打回 {N} 次，需要你介入`。
- 依据一行：`{评审}：{原因}（第 {N} 次）`。
- 按钮：`看原因`（打开原始事件流：时间 + 谁 + 做了什么）、`换人`（弹 `让 {人} 接手？`，确认后提示 `已换人：{人} 接手。{原负责人} 会把源文件交出来。`）、`我来定`（三个选项：`按评审意见改` / `照原样继续` / `先不做这个`）。
- 每条异常必须能点开原始事件，否则不可信。

**底部**
- tab：`概览 / 协作 / 对话 / 复盘`；当前 tab 高亮。
- 输入栏：占位文案 `对全队说… @点名`；右侧 `发送`。发送后：`已发给全队。项目负责人会接住，拆成动作。`；含 @ 时：`已点名 @{名字}，TA 会单独回你。`
- 对话 tab：项目消息流，发件人区分 `你 / 项目负责人 / 成员 / 系统`；@ 消息带「点名」标。输入栏在任意 tab 都在，默认发给项目负责人再分发。
- 复盘 tab：项目一句话复盘、本周完成、打回记录（原因分布）、评审 vs 自评、下一步；数据来自 retro API，不新增叙事。

### 2.4 手机 vs 桌面

| | 手机 | 桌面 |
|---|---|---|
| 首屏 | 只放四样（状态+目标、一张拍板卡、此刻、输入栏） | 三栏同时可见：团队 / 协作流 / 拍板+对话 |
| 团队 | 收进下滑区或「概览」后半段 | 左栏常驻，头像+状态点 |
| 协作流 | 「协作」tab，折叠最近 2 行 | 中栏完整等待图，可展开 |
| 异常 | 概览下滑区，红点提示 | 右栏顶部与拍板并列 |
| 输入 | 底部固定，拇指区 | 右栏底部，支持多行 |

## 3. 三种可颠覆方案：取舍

| | A. 作战室 War Room | B. 办公室平面图 Office Floor | C. 部门频道 + 站会 |
|---|---|---|---|
| 一句话定义 | 一屏三栏：团队状态、协作流（等待链）、拍板+对话，像指挥中心 | 部门是房间，成员是头像，交接物是房间之间移动的小包裹 | 每部门一个频道，每天自动生成站会摘要 |
| 草图 | `[目标·进度] [团队 | 协作流 | 拍板/对话]` | `[内容部 小林● 小琳○] ──📦──▶ [评审部 阿哲●] [设计部 阿美◐ 阿凯▲]` | `#内容部 #设计部 #评审部` + `站会：昨天完成 / 今天计划 / 卡点` |
| 老板三个问题 | 要不要我、谁卡住了、到哪了，全部一屏回答 | 「谁在等谁」好看，但阻塞原因和拍板放不进去 | 还是让老板自己拼全局 |
| 手机适配 | 折叠成纵向分段，体验成立 | 密度低，手机上难做 | 成立，但退回读聊天记录 |
| 风险 | 信息密度高，手机上必须折叠 | 三天后变成装饰 | 与现状没有本质区别 |
| 结论 | **推荐** | 只借「头像 + 状态点」 | 只借「站会摘要」作为复盘入口 |

**推荐 A 的理由**：① 直接对应老板的三个问题，不需要二次解读；② 底层是 dispatch 子任务 + Handoff + 评审的事实投影，不是新增叙事，状态可信；③ 手机折叠成纵向分段后仍成立，桌面可以三栏扩展；④ 借鉴 B 的头像 + 状态点几乎没有成本，借鉴 C 的站会摘要作为复盘入口，避免把主屏做成聊天记录。

## 4. 老板指挥控件

| 老板动作 | 控件 | 位置 | 落地行为 |
|---|---|---|---|
| 下指令（全队） | 输入栏 `对全队说… @点名` | 底部固定，所有 tab 可见 | 发给项目负责人，由它拆解/派单；消息进项目对话 |
| 调优先级 | 协作流行上「置顶」按钮（桌面可拖拽） | 协作流 / 协作 tab | 写 `priority`，负责人重排并通知相关成员；`已置顶「首版文案」，阿哲会先评审它。` |
| 点名追问 | 输入栏 `@名字`，或成员半屏「问 TA」 | 团队 / 输入栏 | 消息 `addressedTo` 该成员，TA 直接回；不经过负责人转述 |
| 验收 / 打回 | 拍板卡 `同意 / 打回并说明` | 需要你 | 打回原因回写成下一轮验收标准补丁；`reviewRound+1` |
| 看复盘 | `复盘` tab | 底部 tab | 读 retro API：完成、打回原因、评审 vs 自评、下一步 |
| 终止 / 改目标 | 顶部 `⋯` 菜单 | 项目标题右侧 | 二次确认；写项目事件；通知全队停下 |

打回规则：原因必选 + 一句话必填；老板原话原样进下一轮执行提示，并作为交接单「验收标准」的补丁。

## 5. 数据映射与新增字段

| 现有数据 / 接口 | 用在工作台哪里 | 需要新增 |
|---|---|---|
| task-folder `departments`（部门 + 成员 bot） | 团队栏分组、成员列表 | 成员 `presence` 不存，由子任务/交接状态推导 |
| `conversations`（每任务一段对话） | 对话 tab、@点名 | 消息加 `addressedTo`、`source: boss/lead/member` |
| `dispatch subtasks` | 进度、团队状态、协作流、等待链 | `blockedOn`（子任务/交接/`boss`）、`waitingSince`、`priority`、`reviewRound`、`authorIds[]`、`reviewerId` |
| `Handoff`（交接） | 交接四件套、协作流行、等待链 | `ackedAt`、`ackBy`、`rejectReason`、`state`（sent/received/returned/consumed/expired） |
| `inbox`（按 `taskId` 归组） | 需要你、异常 | `kind: decision/exception`、`reason` 枚举（对应 5 类拍板点） |
| `retro` API | 复盘 tab | 无（只读） |
| `StateDoc` | 目标、一句话汇报 | 无（只读投影） |
| 项目事件 | 「你不在时」摘要、协作流历史 | **ProjectEvent**：`{ts, taskId, actorId, kind, subtaskId, summary}`；若现有记录能推导则不新建表 |

**新增字段的单位与口径**：
- `blockedOn`：`{type: "subtask"|"handoff"|"boss", id}`；空 = 没被卡。
- `waitingSince`：毫秒时间戳；等待时长 = `now - waitingSince`，只在 `blockedOn` 非空时有效。
- `reviewRound`：该子任务被打回次数；`≥2` 触发拍板点 3。
- `authorIds[]`：写过内容的人（含改过的负责人）；评审硬校验用。
- `reviewerId`：当前评审员；必须 ∉ `authorIds[]`。

**状态推导红线（最容易失败的地方）**：
1. 「受阻 / 等待 / 评审中」只能由子任务、Handoff、评审的事实字段推导，**不允许 bot 自述**；bot 写「我在忙」直接丢弃。
2. 每条异常必须附「看原因」原始事件；没有原始事件的异常不展示。
3. 老板看到的倒计时（已等 6 分钟）必须来自服务端时间戳，不用前端估算。

## 6. 成功指标与观测口径

| # | 指标 | 口径 | 目标 | 数据来源 |
|---|---|---|---|---|
| 1 | 状态可信度 | 异常/等待状态可点开原始事件的比例 | 100% | 事件日志覆盖率 |
| 2 | 阻塞可见时长 | 子任务进入 `blockedOn` → 解除的 p50/p90；手机打开项目到看到「此刻」的时间 | p50 ≤ 5 分钟；p90 ≤ 30 分钟 | `waitingSince`、`blockedOn` |
| 3 | 交接确认时长 | Handoff `sentAt → ackedAt` 的 p50/p90；超时率 | p50 ≤ 10 分钟；超时率 < 10% | Handoff 时间戳 |
| 4 | 评审效率与质量 | 首次通过率、打回原因分布、`reviewRound ≥2` 占比 | 首次通过 60%–85%；≥2 次占比 < 10% | 评审记录 / `reviewRound` |
| 5 | 老板拍板延迟 | 拍板卡创建 → 老板动作的 p50/p90；「稍后」率 | p50 ≤ 1 小时；p90 ≤ 24 小时；稍后率 < 30% | inbox 时间戳 |

**观测节奏**：项目复盘 tab 展示本周指标；超阈值标红并给一条建议。只记时间、枚举、次数，不记录老板正文与语音内容。

## 7. 4 小时只改一处「哇」：项目页顶部「此刻 + 等待链」

- **改什么**：项目页顶部加一行「此刻」，点开后是一条竖向等待链。
- **复用数据**：全部来自 dispatch 子任务的 `status/assignee/updatedAt` 和 Handoff 的 `sentAt/ackedAt`，纯前端推导，不改后端。
- **展示**：`小林 写完文案 → 等 阿哲 评审（已 6 分钟）`；超过 15 分钟的等待变红并出现 `催一下`。
- **催一下**：发一条 @ 消息给被等的人；30 分钟无回应升级为异常。
- **为什么「哇」**：老板第一次能看到团队「在互相等」——这是目前最缺的可见性；且不需要新数据，4 小时能上。
- **验收**：打开项目 3 秒内能看到谁在等谁；每条等待都能追到子任务/交接原始记录。

## 8. 最容易失败的地方与防线

- **最容易失败**：状态不可信——「受阻 / 等待」如果是 bot 自述而不是数据推导，老板看到的就是假仪表盘。
- **第一条防线**：所有状态由 subtask、Handoff、评审的事实字段推导，不允许 bot 自己写「我在忙」。
- **第二条防线**：每条异常必须附「看原因」，点开能看到原始事件；没有原始事件就不显示。
