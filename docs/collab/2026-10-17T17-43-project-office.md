## 1. 运营模式

**角色与权利边界**

| 角色 | 能做 | 不能做 |
|---|---|---|
| 老板 | 改目标/范围、拍板、点名、打回、终止 | 无(但默认不被打扰) |
| 项目负责人(总控 bot,每项目 1 个) | 拆解、派单、调序、换人、汇总、升级给老板 | 评审自己拆出来并参与执行的产出;改目标;对外不可逆动作 |
| 部门 | 认领本部门类型的子任务,内部分配 | 越部门直接改别人的子任务 |
| 成员 | 执行、发交接、提出「阻塞」 | 自评、改派、关闭自己的子任务 |
| 评审员 | 通过/打回(必须写理由) | 修改被审产出 |

**部门间交接**
- 发起方:产出方成员完成后发起,或负责人派单时发起。
- 交接物:Handoff 固定四件:`产出物引用`、`做了什么/没做什么`、`验收标准`、`未决问题`。
- 确认:接收方必须显式「接收」或「退回补件」,退回要写原因。
- 超时:超过 N 分钟没人接收,自动升级给负责人,负责人重派。老板不会直接收到这类事。

**评审与「不能自评」落到权限**
- 在服务端闸门做硬校验:`reviewerId ∉ 该子任务 authorIds[]`。authorIds 包含所有写过内容的成员,也包含负责人(如果它改过)。
- 优先跨部门评审。
- 校验失败返回错误并重新选评审员,不要只在 UI 上置灰。
- 总验收闸门:评审员通过后,仍由老板在「待拍板」里点最终确认。是否免确认由项目的自治等级决定。

**老板拍板点(只有这几类)**
1. 目标或范围变更。
2. 不可逆或对外动作:发送、发布、花钱。
3. 同一子任务被打回 ≥2 次仍未过。
4. 超出自治预算:时间、重试次数、成本。
5. 成员或部门冲突,负责人无法裁决。

**老板不在时的自治**
- 自治信封:负责人可以重派、调序、重试 ≤2 次、跳过非关键项。
- 越界就生成一张拍板卡并停在那里,不要继续硬跑。
- 老板回来时先显示「你不在时」摘要:完成 X 项、卡住 Y 项、需要你 Z 件。

## 2. 主屏(移动端优先的从上到下顺序)

```
┌ 官网改版   [● 等你拍板]                    ┐
│ 目标:4 周内上线新版官网首页                 │
│ ▓▓▓▓▓░░░ 3/7 子任务 · 预计周五完成          │
├ 需要你(2)                                  ┤
│ ⚑ 最终文案可以对外发布吗?                    │
│   评审阿哲已通过 · 小林提交  [同意发布][打回…] │
│ 还有 1 件 ›                                 │
├ 此刻                                       ┤
│ 小林 写完文案 → 等 阿哲 评审(已 6 分钟)       │
├ 团队                                       ┤
│ 内容部  小林●工作中  小琳○空闲               │
│ 设计部  阿美◐等待小林  阿凯▲受阻             │
│ 评审部  阿哲●评审中                          │
├ 协作流                          [全部 ›]    ┤
│ 小林 → 阿哲 交付「首版文案」 等待评审          │
│ 阿美 ⏸ 等小林的文案,已 2 小时                 │
├ ⚠ 异常                                     ┤
│ 「落地页配图」被打回 2 次,需要你介入  [看看]   │
├ [概览][协作][对话][复盘]                     ┤
│ [对全队说…  @点名]                          │
└────────────────────────────────────────────┘
```

**文案与按钮**
- 空态:「团队运转正常,没有需要你的事」。
- 拍板卡按钮:「同意」「打回并说明」「稍后」。
- 状态词固定为:工作中 / 等待 / 评审中 / 受阻 / 空闲。
- 协作流每行格式:`谁 → 谁 · 交付物 · 状态 · 等了多久`。
- 异常卡按钮:「看原因」「换人」「我来定」。

**取舍**:拍板和异常放最上面,目标和进度压成两行。老板第一眼要回答的是「要我干嘛」,不是「项目叫什么」。

## 3. 三个方案

**A. 作战室 War Room**
- 一句话:一屏三栏,左边团队状态、中间协作流、右边拍板和对话,像指挥中心。
- 草图:
```
[目标·进度条·状态]
[团队状态 | 协作流(等待链) | 待拍板 / 对话]
```
- 风险:信息密度高,手机上必须折叠成纵向分段。

**B. 办公室平面图 Office Floor**
- 一句话:部门是房间,成员是头像,交接物是在房间之间移动的小包裹。
- 草图:
```
[内容部: 小林● 小琳○] ──📦──▶ [评审部: 阿哲●]
[设计部: 阿美◐ 阿凯▲]
```
- 风险:很好看,但信息密度低,手机上难做,阻塞原因和拍板放不进去,三天后就变成装饰。

**C. 部门频道 + 站会**
- 一句话:每个部门一个频道,每天自动生成一份站会摘要。
- 草图:
```
#内容部 #设计部 #评审部
站会:昨天完成 / 今天计划 / 卡点
```
- 风险:退回到「读聊天记录」的老路,老板还是得自己拼出全局,和现状没有本质区别。

**推荐 A**,理由:它直接对应老板的三个问题,即要不要我、谁卡住了、整体到哪了。手机端折叠成纵向分段后体验仍成立。可以从 B 借一个东西:团队栏用头像加状态点,这样几乎没有成本就有「办公室」的感觉。C 的「站会摘要」作为复盘入口保留。

打回必须写一句原因。这句原因会成为下一轮 Handoff 的「验收标准」补丁。

## 5. 数据映射

| 现有 | 用途 | 需新增 |
|---|---|---|
| task-folder departments | 团队栏 | 成员 `presence` 由 subtask 状态推导,不存 |
| conversations | 对话 tab | 消息加 `addressedTo`(@点名)和 `source: boss|lead|member` |
| dispatch subtasks | 协作流、进度 | `blockedOn`(subtaskId、handoffId 或 `boss`)、`waitingSince`、`priority`、`reviewRound`、`authorIds[]`、`reviewerId` |
| Handoff | 交接行 | `ackedAt`、`ackBy`、`rejectReason` |
| inbox(按 taskId) | 需要你、异常 | `kind: decision|exception`、`reason` 枚举(五类拍板点) |
| retro | 复盘 tab | 无 |
| StateDoc | 目标和一句话汇报的来源 | 无(只读投影) |

**最关键的一项新增是 ProjectEvent 日志**:`{ts, taskId, actorId, kind, subtaskId, summary}`。「你不在时」摘要和协作流历史都依赖它。如果现有记录已经能推导,就别新建表。

## 6. 4 小时「哇」

**只改一处:项目页顶部加「此刻」一行,外加可点开的「等待链」。**
- 数据:全部来自 dispatch subtasks 和 Handoff,即 `status`、`assignee`、`updatedAt`。纯前端推导,不改后端。
- 展示:「小林 写完文案 → 等 阿哲 评审(已 6 分钟)」。点开后是一条竖向等待链。
- 效果:老板第一次看到团队「在互相等」。这是目前最缺的一块可见性。
- 加分(半小时):超过 15 分钟的等待变红,旁边出现「催一下」按钮,把一条 @ 消息发给被等的人。

## 7. 手机 vs 桌面

**手机首屏只放四样**:
1. 状态胶囊加一句话目标。
2. 一张拍板卡,多的折叠为「还有 N 件」。
3. 「此刻」一行。
4. 底部输入栏。

团队、协作流、异常都收进 tab 或下滑。桌面是三栏,团队、协作流、拍板加对话同时可见,协作流可展开成完整的等待图。

## 反问

1. 一个成员 bot 是跨项目复用,还是每项目一份?这决定「空闲」状态怎么定义。
2. Handoff 现在有没有 ack 状态?如果没有,「接收 / 退回补件」是新增的状态机,工作量比前端大。

---

**最容易失败的地方**:状态不可信。如果「受阻」「等待」是 bot 自述而不是从数据推导,老板看到的就是假仪表盘。

**防线**:所有状态一律由 subtask、Handoff、闸门的事实字段推导,不允许 bot 自己写「我在忙」。

**第二条防线**:每条异常必须附「看原因」,点开能看到原始事件,不然老板不会信。
