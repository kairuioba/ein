# 超长任务（数天～数周、24/7）的上下文与交接设计

> 场景：一个复杂任务要跑一周、团队 24 小时不停；上下文窗口装不下全部历史，换班/换人/重启都可能丢上下文。
> 目标：**大方向不丢、细节可追溯、换人不掉线、成本可控、出问题能回滚**。
> 状态：设计预想（2026-10-17），阶段 A 可以直接开始实现。

## 一、核心原则

1. **状态在文件里，不在对话里。** 对话是工作现场，不是档案室；长期任务的真相必须落盘成可版本化的状态文档。
2. **分层加载，按需检索。** 每一轮只装配「目标 + 当前状态 + 当前子任务 + 直接依赖 + 未决风险」，原始记录永不整体注入。
3. **结构化交接，而不是「自己看聊天记录」。** 换班、换 Bot、重启，交接的是一份固定格式的 Handoff，不是几百条消息。
4. **定时对表，防止跑偏。** 每隔固定时间用「宪法」重新校准目标，主动发现 scope creep（丢了西瓜捡芝麻）。
5. **可恢复、可回滚、可解释。** 任何时刻重启，都能从盘上的状态重建一个「最小但足够」的上下文包。

## 二、五层上下文

| 层 | 内容 | 大小 | 何时注入 |
|---|---|---|---|
| L0 任务宪法（Charter） | 目标一句话、成功标准、硬约束、明确不做（non-goals）、截止时间、预算、验收人 | 300–600 tokens，**永不变**（变更需用户批准并记录版本） | 每次规划/汇总/关键交接 **必带** |
| L1 作战地图（State Doc） | 当前阶段、里程碑状态、进行中/已完成子任务、已做决策（含理由）、未决问题、风险、下一步、花费/用时 | 800–1500 tokens，滚动更新 | 每次规划/汇总**必带**；worker 只带其相关切片 |
| L2 里程碑档案 | 每个阶段的交付物 + 验收证据 + 决策记录；按 ID 索引 | 不整体注入 | 需要时按 ID 取一两个 |
| L3 交接记录（Handoff） | 每次子任务/换班的固定格式记录（见下） | 单条 200–500 tokens | 只注入直接依赖的交接 |
| L4 原始档案 | 完整对话、命令输出、日志、文件历史 | 不设上限 | **永不整段注入**，只能搜索/按引用取 |

> 记忆（MEMORY.md）、资料库（Library）、决策日志、组织事件、复盘记录都是 L2/L4 的现成载体，只需要补 L0/L1 和上下文装配器。

## 三、Handoff 协议（换班/换人/换引擎的最小信息）

每个子任务或每段值班结束时，必须交回一条结构化记录（而不是只给一段话）：

```json
{
  "status": "done | partial | blocked",
  "summary": "一句话：做到哪了",
  "evidence": ["文件/链接/测试输出/验收项 → 在哪"],
  "artifacts": ["产物路径或消息 ID"],
  "decisions": [{"what": "...", "why": "...", "by": "..."}],
  "assumptions": ["..."],
  "openQuestions": ["..."],
  "risks": [{"risk": "...", "impact": "...", "next": "..."}],
  "nextStep": "接手的人第一件事做什么",
  "acceptance": {"criterion": "...", "met": true, "reviewer": "..."}
}
```

规则：
- 没写 `nextStep` 和 `openQuestions` 的交接视为不完整，验收不通过；
- 下游子任务只拿到依赖的 Handoff + 必要上下文切片，不拿全量聊天；
- 总控汇总时逐条核对 acceptance，不允许只转述。

## 四、24/7 长跑的节拍（Cadence）

1. **阶段化**：把「一周」拆成里程碑（天级/半天级），每个里程碑有独立验收；
2. **定时对表**：每 N 小时由总控（或维护机器人）跑一次「状态更新」：
   - 重读 Charter → 当前在做什么？是否偏离？
   - 更新 State Doc（里程碑、决策、风险、花费）；
   - 重新规划未完成部分；
   - 需要人拍板的进「需要你」队列；
3. **漂移检测**：把最近一段实际产出和 Charter 的成功标准比对，发现「在做无关的事/边界外的事」立即停下并上报；
4. **停损规则**：预算用尽、连续失败、停滞过久（watchdog 已有）→ 暂停并升级给人，而不是无限重试；
5. **换班点**：里程碑完成、引擎/模型切换、重启后恢复、人员（Bot）替换，都必须走 Handoff。

## 五、上下文装配器（Context Packer）

每轮发给模型的上下文由装配器按预算拼接，而不是把历史全塞：

```
[Charter 必带]
[State Doc 必带]
[当前子任务 brief/acceptance/boundaries/deliverable/reviewer]
[直接依赖的 Handoff（只取最近一版）]
[未决问题/风险（最多 K 条）]
[最近消息尾部（按 token 预算截断）]
[可选：检索到的 L2/L4（带引用 ID，最多 N 条）]
```

- 每个区块有独立预算（例如 Charter 600、State 1200、依赖 2000、尾部 1500、检索 1500）；
- 超预算时按「对当前决策的相关性」裁剪，并记录「这轮注入了什么、裁掉了什么」；
- 所有长期信息都以**引用 ID** 进入上下文，方便审计「模型当时到底看到了什么」。

## 六、持久化与恢复

- 追加式日志：决策（已存在）、组织事件（已存在）、复盘（已实现）、Handoff（本次要加）——只追加、不回改；
- State Doc 用原子写 + 版本号，旧版本保留在 `backup`/资料库版本里；
- 重启恢复 = Charter + State Doc + 未完成子任务及其 Handoff，**不 replay 聊天记录**；
- 每周（或每个里程碑）做一次「档案对账」：State Doc 的建设 vs 实际产物/证据，不一致以证据为准并记录。

## 七、防「丢西瓜捡芝麻」的具体检查

| 风险 | 检查 | 动作 |
|---|---|---|
| 目标漂移 | 每 N 小时对照 Charter 的 non-goals / 成功标准 | 偏离则停下、上报、重新规划 |
| 只做小事 | 里程碑验收 + 「本周最大产出是什么」必答 | 没有推进里程碑 → 升级 |
| 交接失真 | Handoff 必须带 evidence/nextStep | 不完整 → 验收人打回 |
| 上下文丢失 | 每轮装配器记录注入清单 | 关键决策找不到依据 → 回查 |
| 成本失控 | 预算线 + 每阶段花费上限 | 超限暂停，等人批准 |
| 任务无限延长 | 截止时间 + 阶段停损 | 到期未完成 → 交付当前最好结果并说明 |

## 八、在 Ein 里的落地计划

| 阶段 | 内容 | 依赖 |
|---|---|---|
| A | `DispatchRun` 增加 `charter` 与 `state` 文档；`POST /api/dispatch/runs/:id/checkpoint` 更新状态；规划/汇总/worker 提示词注入（带预算） | 现有 dispatch 结构 |
| B | Handoff 结构化字段进入 worker 提示词与存储；验收人据此判定；总控汇总引用 | 阶段 A + 验收闸门 |
| C | 定时监督 routine：每 N 小时更新 State Doc、重规划、漂移检测、进「需要你」；停损规则 | 阶段 A/B + routines |
| D | 上下文装配器 + 资料库/档案检索（带引用与注入清单） | 阶段 A |
| E | 多天恢复测试（杀进程/重启/换引擎）、漂移审计、复盘指标 | 阶段 A–D |

**建议从阶段 A 开始**：不需要新引擎能力，纯服务端字段 + 提示词 + 一个接口，就能让长任务的「大方向」第一次变成可持久化、可注入、可校准的东西；做完用真实长任务压测，再决定 B/C 的优先级。

## 九、判断是否成功的指标

- 目标对齐率（每次对表是否仍在 Charter 范围内）
- 里程碑准点率 / 交付被验收一次通过率
- 交接完整率（Handoff 必填项齐全）
- 长任务平均人工干预次数（越低越好）
- 每里程碑花费与总预算偏差
- 重启/换班后的恢复时间与丢工率
