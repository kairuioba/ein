## Claude 的回答

`★ Insight ─────────────────────────────────────`
- gate 的 fail 应该只表示"我验证了，结果不对"。"没法验证"是另一种结论，所以你把它改成 needs_human 是对的。
- 这次冒烟暴露的是协议依从性和运行环境（cwd）问题，不是调度引擎问题。
`─────────────────────────────────────────────────`

**1. 改动方向对，但 synthetic 要加三条约束**
- synthetic handoff 的作用只是让下游有内容可读，不能让它掩盖不合规。
- synthetic 的 gate 结论永远不得是 pass，最多 needs_human。
- `handoff.source='synthetic'` 要落库，并在 UI 上显示"未按格式交付"角标。
- 按 model 记一个计数，统计"未交信封率"。不用做看板，日志或 transcript 里能 grep 到就行。
- 不要做成静默兜底。没有这三条，synthetic 就会掩盖问题。
- 备选方案是不生成 synthetic，直接 needs_human 并让下游阻塞。这样更"诚实"，但弱模型会让整条链卡死，所以不推荐。
- artifact 无 cwd 判 unverifiable 是对的。真正的根因是 worker 没有默认 cwd，应该默认给任务文件夹作 cwd，这比判 unverifiable 更值得修。

**2. 收件箱合并：后端出分组投影，前端只渲染**
- 底层 item 保持原子，各自有状态，便于审计和幂等处理。后端提供按 taskId 聚合的卡片视图 `{taskId, items[], counts, priority}`。
- 角标和未读数必须由后端算，前端自己分组会让数字不一致。
- 点击：卡片整体点击进入任务窗口（已关闭则只读）。卡片内联展开后，每项有自己的操作。
- 卡片状态由 items 推导：任一项 pending 则整张卡 pending，显示"2/4 已处理"；全部处理完才消失。
- 同因的 needs_human（例如 3 条"未交信封"）折叠成一行"3 个子任务未按格式交付"，只提供一个"已知悉"操作。
- signoff 固定置顶，且不参与批量操作。若还有未处理的 gate，签收时二次确认"仍有 N 项未处理"，再写 acceptedAt。
- 不做跨任务批量处理。

**3. 不交信封的改进，按成本从低到高**
1. 接受 synthetic：已完成，成本 0。
2. prompt 加一句：成本约 0，现在就做。放在 prompt 末尾，要求"最后一条消息以信封代码块结尾"，并附一个最小示例。
3. 补信封重试：多一轮短对话（"只输出信封"），成功率高，但要限定最多重试 1 次。时间紧就先不做，留到下一版。

**4. 4:30 前的清单**

必须做（3 项）：
1. worker 默认 cwd 设为任务文件夹，同时在 prompt 末尾加信封强调句。
2. 收件箱后端按任务分组投影，前端渲染卡片和展开，signoff 置顶。
3. 用真机重跑一次冒烟，确认三个子任务不再出现 gate_failed、收件箱只剩 1 张卡，然后补上本次改动的回归测试并提交、打包。

明确不做：
- 补信封重试。
- 按 model 的依从性看板。
- 跨任务批量操作和自动放行 gate。
- gate 语义的进一步改动。
- 收件箱动效和视觉打磨。
- fork 流程的细节完善。

**这次真机冒烟最能说明的问题**
- 派单、完成、关闭、409、signoff 这条主链路在真实模型下跑通了，引擎本身是稳的。
- 薄弱点是与真实模型的格式契约和运行环境（cwd），不是调度。
- 之前"无法验证就算 fail"的默认值会制造大量误报，淹没真正需要人看的 signoff，所以收件箱的注意力噪声才是最大的产品风险。
