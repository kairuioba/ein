`★ Insight ─────────────────────────────────────`
- 这类系统最常见的缺陷是「决定被记下来了，但状态机没动」。收件箱的 resolve 只是审计记录，任务状态必须在同一个事务里由单一入口迁移。
- 现在 approve、reject、signoff 各走各的路，所以会出现「收件项已处理，任务却卡住」。

## 1. 最可能出错的 5 点（按严重度）

**① approve gate_failed 只记 override，不推进状态。应该更新。**
- 现在的后果是：收件项消失了，folder 还停在 gate_failed 或 running，任务永远到不了 done。下游依赖不解锁，窗口不 closedAt，「已完成」列表里也看不到它。
- approve 应当等价于 pass 的全部副作用，也就是和 pass 走同一个 `acceptFolder(folderId, {via:'override', by:'owner', note})`。
- 要有 `acceptedVia: gate|override` 字段，UI 显示「人工放行」。
- 上下文注入时要带这个标记，下游才知道这份产出没过闸门。

**② signoff 只记 resolution，等于空操作。**
- 先确认它是 folder 级还是 task 级。我猜是「闸门 pass 后或 needs_human 时的最终确认」。
- approve 的处理：folder 接受，若全部 folder 已接受则 task 变 done 并写 closedAt。
- reject 必须带一句话，复用 `dispatcher.rework`（folder 级）。若是 task 级，就把任务重开（closedAt 置空）并把这句话作为消息发给总控。
- 现在 needs_human 的 signoff 一旦 approve 没效果，旧 acceptance 映射出来的任务（全是主观标准）会全部卡死。这是影响面最大的一条。

**③ 多次打回：收件项重复和过期 attempt。**
- 给收件项加唯一键 `(folderId, attemptId, kind)`。
- rework 时在同一事务里完成三件事：旧项置 `superseded`，建新 attempt，之后 attempt N+1 的 gate_failed 才创建新项。
- 并发点击要用 CAS 防住：`UPDATE inbox SET status='resolved' WHERE id=? AND status='open' AND attemptId=?`，并检查 `changes==1`。只在 handler 里读后比较（`expectedAttemptId`）是不够的。
- attempt N 的 worker 结果可能在 N+1 开跑后才回来。gate 和结果写入必须按 attempt 过滤，过期的直接丢弃，否则会冒出一个指向旧 attempt 的幽灵 gate_failed。
- 加 rework 次数上限（比如 3 次），超限后只允许 approve 或 abandon，否则会无限烧钱。

**④ closedAt 只在 done 时打，是错的。**
- cancelled 是终态，必须 closed，否则向已取消的任务发消息会含糊地「复活」它。
- failed 可以保持开放（允许重试），但要明确：发消息 = 显式重派，不能静默进行。owner 选 abandon 后变 cancelled，同时 closed。
- 别让 `closedAt` 和 `status` 两处各存一份真相。所有终态迁移都走一个 `transitionTask()`，在里面统一写 closedAt。
- 发消息的 409 校验要和消息插入放在同一事务里，否则「done 的瞬间正好有消息进来」会漏过去。

**⑤ 上下文注入和 fork 会把没接受的内容当事实。**
- 只注入已接受（pass 或 override）的产出，并标注来源和是否 override。被打回的 attempt、failed 的内容不要注入。
- 前序 worker 的输出是不可信文本，要用引用块包起来标成数据，防止 prompt 注入。
- 大小按 token 限制，不要按字符。
- `clientRequestId` 的唯一键应该是 `(sourceTaskId, clientRequestId)`，不要全局唯一。
- fork 一个还没完成的源任务时，注入内容为空或带警告，别静默注入半成品。

## 2. LLM reviewer 最小方案

**推荐：本版不做，只保留 needs_human，但把接口预留好。** 理由：

- **隐藏 turn 复用任务窗口：不要。** 它会污染窗口历史和上下文，让总控「自己审自己」产生偏见，还会让 closedAt 窗口的写入语义变复杂。
- **专用 reviewer 会话：可以做，是下个版本的正解。** 最小路径如下：
  1. 定义 `ReviewerPort.review({criteria, result, handoff, artifactsExcerpt}) → {criterionId, verdict, reason}[]`。
  2. 每次 gate 新开一次性会话，无工具、无历史，输入有界，输出严格 JSON，用 schema 校验。
  3. 解析失败或超时（60 秒）一律 needs_human。
  4. v1 策略：LLM 说 pass 就计入并标「助审」；LLM 说 fail 只升级为 needs_human，**不自动打回**。不让一个模型的意见直接触发重跑，避免成本和循环风险。
- 现在加这个要多一套会话生命周期、成本记账和失败路径，4 小时和 2 次调用不够。

## 3. 10 步冒烟清单

1. 启动 dev 包，侧栏任务列表渲染，「进行中」和「已完成」折叠正常，没有任务时不报错。
2. 点「新建任务」，窗口、folder、侧栏项同时出现。刷新后仍在，并确认只建了一个窗口。
3. 在窗口里让总控派一个子任务，run 挂到预建 folder，不再新建 folder。
4. 造一个会失败的闸门（比如 criteria 要求 artifacts 但 worker 不产出），确认 gate_failed 入箱，侧栏出现 needs-you 角标。
5. 在收件箱点 seen，角标消失但项目仍在。再制造一个 needs_human 的 signoff（旧 acceptance 任务）。
6. **打回，最可能坏的一步。** 带一句话 reject，检查：新 attempt 创建；worker prompt 里有 reworkNote；旧收件项变 superseded；只剩一个 open 项；快速连点两次只生效一次。
7. approve 一个 gate_failed 和一个 signoff，检查任务是否真的变 done、窗口是否 closedAt、「已完成」列表是否出现。这一步按我的判断**现在会失败**。
8. 向已完成窗口发消息，期望 409 TASK_CLOSED 且带 `canFork:true`。再对 cancelled 和 failed 的窗口各试一次，对照第 1 节第④点的预期。
9. 点「基于此新建」：新窗口出现，有草稿，没有复制旧消息。快速双击只产生一个窗口（幂等）。
10. 在 fork 出的窗口里派单，抓 worker prompt，确认注入了源任务的有界上下文，且 override 或被打回的内容有正确标注或被排除。

**最可能坏的步骤是第 6 步，其次是第 7 步。**
- 第 6 步的判断方法：查 attempts 表和 inbox 表，看 `status='open'` 的行数是否恰好为 1，再 grep worker 实际收到的 prompt 里有没有 reworkNote。
- 第 7 步的判断方法：approve 后查 task 和 folder 的 status 是否变化。没变就是确认缺陷。

## 4. 剩 2 次调用：做什么、砍什么

- **第 1 次：补状态机。**
  1. 统一 `transitionTask()`，终态包括 done 和 cancelled，在里面写 closedAt。
  2. approve override 和 signoff approve/reject 都走真实迁移，复用 `rework`。
  3. 收件项加唯一键、CAS 和 supersede，gate 结果按 attempt 过滤，加 rework 上限。
  4. 同时补这三处的测试：approve 后状态、两次打回后恰好一个 open 项、cancelled 发消息返回 409。
- **第 2 次：留给 dev 构建冒烟后的修复。** 冒烟一定会暴露问题。这一次也顺便收尾：提交 `docs/collab/transcript.jsonl` 的修改，并让注入只带已接受的内容。
- **明确砍掉：** LLM reviewer、fork 复制消息、批量收件箱操作和过滤、abandon 的精细 UI、视觉打磨、多 owner。
