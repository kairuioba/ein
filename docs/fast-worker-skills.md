# 快同事的经验提炼与复现（研究稿，下个版本再迭代）

> 2026-10-17 老板提出的自我迭代思路：任务里总有人快、有人慢。任务负责人可以总结「为什么快」，看能不能沉淀成 skill，再在同部门复现。
> **本版不做**：可能涉及超长上下文、很费 token，先研究方案，下个版本再迭代。

## 一、目标

把「某个同事这次做得又快又好」变成三类可复用资产：

1. **提示词模板（skill）**：它的 brief 结构、约束、示例、验收要点；
2. **派单模板**：这类子任务该拆几步、依赖怎么排、给什么模型/强度；
3. **部门打法**：同部门其他同事照着做，验收标准保持不变。

## 二、从哪些信号判断「快且好」

- 子任务耗时低于同角色中位数（`durationMs`，来自复盘记录 `dispatch-retros.ndjson`）；
- 一次通过、无重试（`attempts === 1`）；
- 验收人按原验收标准判过（不是靠降低标准换来的快）——**审核标准不变是前提**；
- 没有返工/返修记录（review 或下游任务没有打回）；
- 模型/强度、输入材料量、工具使用方式。

## 三、提炼流程（任务负责人执行，总控汇总）

1. 任务结束时读复盘：找 `fast + first-pass` 的子任务；
2. 让该员工交一份「我是怎么做的」三行说明：关键步骤 / 省时技巧 / 容易踩的坑；
3. 负责人把这些与原始 brief、验收标准对照，产出 `SkillDraft`：
   - 适用任务类型、角色；
   - 推荐 brief 结构（含边界/交付物/验收）；
   - 关键步骤与顺序、常见错误；
   - 一次可验证的「标准答案」示例（脱敏后）。
4. 审核标准**不修改**；skill 只影响怎么做，不影响算不算过。

## 四、复现方式（同部门内，控制成本）

- 同部门后续同类子任务，brief 末尾附上 `SkillDraft`（短版，≤400 tokens）；
- 只注入「方法/结构」，不注入该员工的具体数据上下文，避免数据串味；
- 先 A/B：一半同类任务带 skill、一半不带，比较一次通过率与耗时；提升明显才默认启用。

## 五、长上下文与 token 成本（为什么本版不做）

- 「我是怎么做的」全文可能很长；直接塞进下个任务会污染上下文，且 token 贵；
- 方案：只提炼**结构化短卡**（步骤/要点/坑），不保存原始长对话；
- 把 skill 存成部门资料，按需检索注入（类似资料库订阅），而不是每轮都拼进 prompt；
- 每次注入记录「注入了哪个 skill、多大」，方便审计和成本控制。

## 六、分阶段计划

| 阶段 | 内容 | 验收 |
|---|---|---|
| 1（下个版本） | 复盘记录里增加「快且一次通过」标记；负责人可手动生成 SkillDraft（结构化短卡） | 能对一次真实任务产出 1 个 skill 卡 |
| 2 | 同部门同类任务自动附短卡；记录带/不带 skill 的对比 | 一次通过率或耗时有不回退的改善 |
| 3 | 总控按部门汇总 skill 库；清理无效 skill | skill 数可控、注入成本可见 |
| 4 | 审核标准保持不变的前提下，纳入自我迭代闭环 | 指标可解释、可回滚 |

## 七、风险

- 把「快」误判成「偷工减料」：必须绑定验收通过 + 审核标准不变；
- skill 过拟合单一任务：只按「任务类型 + 角色」复用，先 A/B；
- token 成本失控：短卡 + 按需注入 + 每次记录大小；
- 数据隔离：skill 只沉淀方法，不沉淀该员工看到的数据。
