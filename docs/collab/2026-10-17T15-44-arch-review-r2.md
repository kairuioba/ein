## 1. Bot 归属与释放

**结论**：Bot 是「角色/能力」，不是「任务容器」。任务完成后释放，但每个新任务都开新的引擎 session，不续用旧 session。

**状态机**：`idle → bound(taskId) → idle`。任务归档后，旧 task 的 session 只读，不可 resume。

**理由**：串味的来源不是 Bot 复用本身，而是 session 上下文和 Bot 级持久物。session 隔离能挡住对话上下文。挡不住的是下面这些，所以释放时要显式清理：
- Bot 级长期记忆或人设里被写进的任务事实。
- 共享 workspace/cwd 里的残留文件。
- 引擎侧缓存的工具状态。

**可执行动作**：
- Bot 加 `currentTaskId: string | null`。派单选人只选 `currentTaskId == null` 的 Bot。
- task 加 `status: active | done | archived` 和 `releasedAt`。`done` 时由代码置 `bot.currentTaskId = null`。
- 释放钩子里做三件事：关闭该 task 的引擎 session；清理该 task 的 scratch 目录；禁止任务事实写入 Bot 级记忆（只允许写角色偏好）。
- **控池策略**：按部门池，不做能力标签匹配。每个部门设 `maxBots`。无空闲 Bot 时，任务排队，或在上限内「加人」。不要每个任务新建 Bot。
- 20 个任务之后，Bot 数不增长，增长的只有 `bot.tasks[]`。对 `archived` 的 task 只保留 summary 和 State Doc，session 引用可清除，并且不计入活跃数。

## 2. 验收闸门最小实现

**结论**：先跑零成本的确定性检查，再对风险子任务做一次异模型 LLM 审查。

**Reviewer**：用与 worker 不同引擎或不同模型的、更便宜的模型。跨模型的目的是降低共同盲区。

**输入**（只给这些，不给 worker 的思考过程）：
- 派单时由总控写入 `subtask.acceptance[]`（每条有 `id` 和可判定的描述）。
- `DispatchHandoff` 信封。
- 产物清单加 diff 或文件路径。
- 边界/禁区（`subtask.constraints`）。

**输出 schema**：
```ts
type ReviewResult = {
  verdict: 'pass' | 'fail' | 'needs_human'
  criteria: { id: string; met: boolean; evidence: string }[]
  blockers: string[]
  fixHint?: string
  failClass?: 'incomplete' | 'wrong' | 'out_of_scope' | 'capability'
}
```

**失败处理**：
- `fail` 时同一 worker 重做一次，把 `blockers` 作为反馈，`attempts+1`。
- 第二次仍然失败，就升级给任务负责人（`needs_human`）。
- 只有 `failClass == capability` 才允许换模型，而且是人确认后换，不自动换。

**成本控制**：
- 第一层是确定性检查，每个子任务都跑：信封能解析、声明的产物存在、测试/lint 通过（如果有）。
- 第二层 LLM 审查只对三类子任务做：有产物落地的、被 ≥2 个下游依赖的、run 的最终汇总。
- 其余子任务只过第一层。

**人工抽检**：
- 100% 看 `needs_human`。
- 随机 10% 看 `pass`，前两周提到 30%。
- 100% 看 reviewer 与确定性检查冲突的。
- 抽检结果写入已有的 dispatch-retros，用来校准 reviewer。

## 3. State Doc

**代码写的事实字段**：
- `taskId`、`runId`、`ownerId`、`rev`、`updatedAt`
- 子任务表（`id/status/attempts/assignee`）
- `artifacts[]`（路径、hash、来源子任务）
- 各子任务 handoff 的引用
- 评审 verdict
- 失败/报错摘要
- 成本和 token

**模型写的判断字段**：
- 目标复述
- `decisions[]`（含 why）
- `openQuestions`
- 风险
- `nextStep`
- 假设

**只留 6 个字段**：
1. `goal`：模型写，创建时由人或总控确认，之后不改。
2. `subtasks`：代码生成。
3. `artifacts`：代码生成。
4. `decisions`：模型写，append-only，每条必须带 why，设条数上限。
5. `blockers`：代码填报错，模型补原因。
6. `nextStep`：模型写，只保留一条。

**规则**：每次更新由代码重算事实字段，不采信模型自报的状态。模型字段只能追加或覆盖自己的字段。`rev` 单调递增，换模型/续跑时带上 `rev`。

## 4. 统一 Handoff

**结论**：一个信封，加 `kind` 区分场景。State Doc 是事实源，信封是 State Doc 加本次增量的快照。

**必填（所有场景）**：
```ts
{ kind: 'result' | 'continue' | 'switch_model',
  taskId, subtaskId, attemptId,
  status: 'done' | 'partial' | 'blocked' | 'failed',
  summary, artifacts[], openIssues[], nextStep }
```

**按场景附加**：
- `result`：`acceptanceSelfCheck[]`、`confidence`。
- `continue`（长任务交接）：`stateDocRev`、`resumePoint`。
- `switch_model`，最小额外信息只要这四项：
  1. `switchReason`（为什么换）。
  2. `triedAndFailed[]`（试过且失败的做法，防止新模型重蹈覆辙）。
  3. 当前工作区状态引用（diff 或 commit，不要贴全文）。
  4. `acceptance[]` 原文。

不要把旧模型的完整对话塞给新模型，那是最大的串味来源。

## 5. 幂等/防重复

**结论**：单进程 Node 不需要分布式 lease。`attemptId` 加 `bootId` 就够，可以复用现有 `status/attempts/threadId`。

**新增字段**：
- `subtask.attemptId`：每次派发生成 uuid。
- `subtask.bootId`：派发时的进程启动 id。
- `subtask.heartbeatAt`：可选。

**判断逻辑**：
1. 派发：在同一个同步 tick 内检查 `status == pending`，置 `running`，写入 `attemptId/bootId` 并落盘，然后才 spawn。检查和置位之间不能有 `await`。
2. 启动恢复：扫描所有 `running` 且 `bootId != currentBootId` 的子任务，一律置 `interrupted`，不直接重派。
3. 对 `interrupted` 的子任务：
   - 如果 `threadId` 对应的 session 能查到已有产出，就先收取结果。
   - 否则 `attempts+1`、换新 `attemptId` 再派。
   - 对有外部副作用的子任务（发消息、写外部系统），默认不自动重派，转人工。
4. 结果提交：只接受 `result.attemptId == subtask.attemptId` 的结果，其余当作过期结果丢弃并记日志。这条能同时防旧 worker 晚到的结果覆盖新结果。
