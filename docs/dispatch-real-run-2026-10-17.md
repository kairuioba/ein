# 真实派单实测记录（2026-10-17，dev.14）

> 目的：用本机真实引擎跑一个虚拟但完整的任务，验证「派单」核心链路（自动提示词、依赖、并行、汇总）。
> 任务由我在总控对话里用 API 直接发起，全程未改任何文件（任务里也明确禁止了）。

## 环境

- 版本：`1.1.3-dev.14`，渠道 dev，维护岗正常；
- 引擎：总控 = WorkBuddy · Deepseek-V4.1-Flash；子任务按推荐用到 Codex · GPT-6.1-Sol（max effort）与 WorkBuddy · MiniMax-M3；
- 派单设置：autoCreate 开、maxConcurrent 3、maxSubtasks 8、autoSynthesize 开、requireApproval 关。

## 任务

《一念 Ein 新用户 5 分钟首体验方案》一页纸，要求含：3 条现状/竞品观察（带依据）、≤5 步体验脚本、逐步验收标准与验收人、明确不做/边界、风险与缓解；要求先拆解派发、标明依赖与验收人，最终由总控汇总并**逐项引用员工实际交付**。

## 实际发生

1. 总控调用 `submit_plan`，一次生成 4 个子任务并**自动创建 4 个专员**：
   - `s1 现状与竞品观察 3 条` → 产品市场研究员（WorkBuddy/MiniMax-M3）
   - `s2 5 步首体验脚本` → 产品体验设计师（Codex/GPT-6.1-Sol，max），依赖 s1
   - `s3 逐步验收标准与边界` → 质量验收负责人（WorkBuddy/MiniMax-M3），依赖 s2
   - `s4 风险清单与缓解` → 运营风险分析师（WorkBuddy/MiniMax-M3），依赖 s1、s2
2. 每个子任务的 `brief` 是软件自动生成的完整员工提示词：背景、边界（禁止改文件/写代码）、逐项要求、硬约束、输出格式、验收标准（如「3 条、单句、每条带依据标注、无编造数据」）都在里面。
3. 依赖按顺序执行：s1 → s2 → s3；s4 并行启动；全程约 9–10 分钟（含 Codex max effort）。
4. 4 个子任务全部 `done`，产出质量：
   - s1 三条观察均带「依据」标注，明确区分通用认知/推断；
   - s2 五步脚本每步含步骤名/看到什么/做什么/耗时，合计 255 秒；
   - s3 逐步验收标准可判定（≤60 秒、≤5 秒、恰好 3 项等），并给出验收人及理由；
   - s4 三条风险含触发步骤、影响、可执行缓解、责任角色。
5. 总控汇总：一页纸按 s1–s4 分节，**每节标注 @成员**，明确说明哪些是推断、哪些需要用户决策，末尾给出「未验证项：全部为方案层文本、没做真实用户测试」，**没有替员工补写或夸大交付**。它还主动指出「验收人里没有你本人」并询问是否需要用户签某一步。

## 发现的问题

| # | 问题 | 处理 |
|---|---|---|
| 1 | 计划结构里只有 `brief` + 可选 `acceptance`：**边界、交付物、验收人没有结构化字段**，只能写在 prompt 文本里 | 本轮已改：`boundaries` / `deliverable` / `reviewer` 进入计划 schema、校验、员工提示词、汇总要求和 UI（reviewer 缺省=总控） |
| 2 | 总控第一回合弹出一个审批卡，tool 名显示为 **“tool”**（引擎名缺失），用户看不懂在批什么 | 记入 backlog（WorkBuddy/ACP 权限请求的工具名映射要补） |
| 3 | 任务总耗时约 9–10 分钟（Codex max effort 较慢），但全程没有卡死；期间唯一一次人工操作是批准那张卡 | 无（可作为「长任务」基线） |

## 结论

派单主链路（拆解 → 自动提示词 → 依赖/并行 → 汇总 → 不夸大）**在真实模型上跑通了**。本轮补上了「派单总库」的结构化字段（边界/交付物/验收标准/验收人），下一版 dev 构建后可用新字段再跑一次对比。
