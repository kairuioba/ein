## Q1 最该优先改的 3 个结构性问题

**① 验收闸门缺位(P1 还没做),所有"自动化"都建在没人把关的地基上**
- 判断:现在"完成"≈ 模型自称完成。`acceptanceMet` 只是自评,reviewer 还停在设计稿。
- 理由:快同事复用、重新派活、自我迭代、长任务对表,全都依赖"完成且合格"这个信号。信号不可信,后面全是放大器。
- 建议动作:先做一个最小 reviewer。独立会话、不同模型、只读、输入只有验收标准加产物,输出 pass/fail 加理由。没通过不进下游依赖,也不进复盘的"成功"。
- 不做的代价:错误会沿依赖链传递,后期要回溯重跑整条链,而且复盘数据是脏的,以后没法用来 A/B。

**② 任务归属模型在多处各存一份,迁移风险被低估**
- 判断:`bot.section`、`OrgDepartment.taskId`、`bot.taskId`、`run.id` 加 `TaskFolder.id`,同一件事在 4 处表达。
- 理由:阶段 3 是"中高风险",而且已有"run 自动同步成文件夹"和"首启迁移最近 12 个 run"。两个来源同时写同一实体,最容易出现孤儿和重复。
- 建议动作:确立单一真相。Bot 的归属只由 TaskFolder 里的 `members` 表示,`bot.taskId` 做派生缓存。阶段 3 开工前先写不变量检查,例如每个 Bot 最多一个活跃任务、部门必有任务。
- 不做的代价:数据一旦脏了,用户在侧栏看到的"乱"会比现在更难修。

**③ 状态都在对话里和 JSON 里,没有统一的"可重建的真相源"**
- 判断:Charter、State、Handoff、复盘、任务时间线分散在多个文件和字段里,没有装配器,也没有注入清单。
- 理由:long-horizon 的整套机制都靠"每轮由装配器拼上下文"。目前只有注入,没有预算和审计。
- 建议动作:先做一个纯函数 `packContext(run, subtask)`,返回 `{text, manifest}`,只做截断和记录,不做检索。
- 不做的代价:数天任务一旦出错,你无法回答"模型当时看到了什么"。

## Q2 任务文件夹模型

**判断:方向对,但"Bot 同时只属于一个任务"这条硬规则,在没有"释放"语义时会让 Bot 数量失控。**
- 理由:
  - 任务做完后 Bot 归谁?文档说"已完成不归档",那 Bot 就一直被占着。第二个任务只能新建 Bot,Bot 会越攒越多,预算和编制压力也随之而来。
  - 总控、任务负责人、部门负责人是三层,权限边界只写了"不能混",没有定义哪些动作归谁(加人、改验收标准、动预算)。
  - 同名部门分任务各存一份,UI 和成本统计上容易被当成同一个部门。
  - "不跨任务借人"和"快的 Bot 不能闲着"在任务边缘直接冲突,最后一个任务收尾阶段全是空闲 Bot。
- 建议动作(更简单的路径):
  1. 把"属于一个任务"改成"**绑定一个会话上下文**"。Bot 是能力,会话才是任务内的实例;任务完成时释放会话,Bot 回到池里。
  2. 这样"上下文不串味"这条真正的目标由会话隔离保证,而不是靠"Bot 只属于一个任务"。
  3. 权限写成一张表:动作 × 角色(总控 / 任务负责人 / 部门负责人)。不要靠文字约定。
  4. 同名部门的 UI 里强制带任务色标。

这一点我只读了文档,没读代码,所以实际的 Bot 与会话的映射关系需要你们确认。

## Q3 信封与派发

**设计过度的部分:**
- `permissions` 里的工具白名单:各引擎的工具体系不同,没有统一执行层就没法强制,写在信封里只是自觉。
- `limits.maxTokens`、`budgetCny` 这类字段,在引擎不上报用量时无法执行。
- "补信封"重试和 `engineReportedUsage` 这类容错,先等出现实际失败再做。
- 路由里"能力 → 成本 → 负载 → 本地/云"四层,目前只有推荐器就够了。

**不够的部分:**
- 没有幂等和防重复:异步 run 重启后,同一个子任务怎么避免被派两次?
- 没有"谁有权改信封里的验收标准"。现在子任务可以在 handoff 里自评 `acceptanceMet`,验收标准的版本没锁住。
- 异步 run 里"总控汇总"依赖信封,但没有定义"部分子任务失败时是否继续汇总"。

**下一版最小闭环:**
- 保留:Send/Result 信封核心字段、容错解析、`meta.tokens/cost/model`、独立 reviewer 的 pass/fail、一次换模型重试。
- 砍掉:工具权限强制(先靠提示词和只读/读写两档)、await 模式、完整回退矩阵(只留"限流换引擎、验收失败换更强模型"两条)。
- 先证明一件事:同一份信封能让 3 家不同模型的输出被同一个 reviewer 稳定判定。

## Q4 长任务

**最容易失败的点:State Doc 靠模型自己更新,会慢慢漂。**
- 理由:
  - 每次对表都由模型改写 State Doc,错误会累积,而且难发现。
  - "漂移检测"本身也是模型判断,一个会漂的模型来检测漂移,可信度有限。
  - 停损规则里"停滞过久"依赖 watchdog,和任务进度不是一回事。
- 建议动作(最小可验证实现):
  1. State Doc 里的事实字段(已完成子任务、花费、里程碑状态)**由代码从 run 数据生成**,模型只能写"判断"字段(风险、下一步)。
  2. 对表 routine 只做三件事:重生成事实、对照 Charter 的 non-goals 做一次检查、把需要人的事推到"需要你"。
  3. 做一个杀进程重启测试:kill 掉服务,重启后能否仅凭 Charter + State + 未完成子任务继续跑,而不依赖聊天记录。这是比"目标对齐率"更硬的验收。
- 不做的代价:跑一周之后你会发现 State Doc 描述的世界和实际产物不一致,且找不到哪一次开始错的。

## Q5 快同事 → skill

**判断:这个方向有问题,至少"提炼成 skill"这一步先别做。**
- 理由:
  - "快 + 一次通过 + 验收通过"在验收人和验收标准本身没被验证的前提下,仍然可能是低标准下的快。文档说"审核标准不变是前提",但没有机制保证这一点。
  - 样本太小。一个子任务快,可能只是任务简单、材料少,和方法无关。
  - 让员工自述"我是怎么做的"是事后合理化,和真实原因常常不是一回事。
- 建议动作(替代方案):
  1. 先做**对比而不是提炼**:同类任务里,用 diff 看快的和慢的产出有什么结构差异(步骤数、引用来源数、产物长度),用数据说话。
  2. 有稳定差异后才生成 SkillDraft,并且必须通过**反向测试**:用同一个 reviewer、同一套验收标准、**更严的抽检**,对"带 skill"的产出做回归,通过率不低于基线才启用。
  3. skill 只能由负责人审批启用,不能自动注入。
  4. 先把 Q1 的验收闸门做好,这一步才有意义。

## 一件事

**先做独立 reviewer 的验收闸门(不同模型、只读、pass/fail),并让复盘只统计通过闸门的结果。**
这是 Q1、Q3、Q5 共同的前提,没有它,重新派活、自我迭代、长任务对表都在放大未验证的结果。
