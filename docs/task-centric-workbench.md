# 任务式工作台：从「公司总览」改成「按任务文件夹」

> 2026-10-17 设计稿。问题：现在工作台和侧栏是「全公司一张图」——研发部、未分部门、各种派单混在一起；任务一多就排不下，也看不出某个部门属于哪个任务。
> 结论：**任务是最外层容器**。每个任务像一个文件夹（颜色 + 序号 + 可折叠 + 可拖拽排序），任务下面是它的总负责人，再下面是**只属于这个任务**的部门，最后才是成员和产出。工作台一次只看一个任务，不再做「总工作台」。

## 一、信息架构（IA）

### 侧栏（任务文件夹）

```
🔍 搜索 Bot、群聊、文件…

简报   工作台   日历   资料库   连接应用

────────────────────────────────────────
任务                                  + 新建
  1 ● 发布会筹备           总控 ⭐ 进行中 3/4    ▾
      └ 研发部   (3)  负责人 阿码        ▸
      └ 市场部   (2)  负责人 小文        ▸
  2 ● 用户访谈提纲         总控 ⭐ 已完成         ▸
      └ 研究部   (2)  负责人 小研        ▸
  3 ● 官网改版             总控 ⭐ 待启动         ▸
────────────────────────────────────────
未分派（不属于任何任务的 Bot）        ▸
  研发部 … / 未分部门 …
────────────────────────────────────────
凯瑞 · 本周用量 1%      ⟳   ⚙
```

规则：

- **任务**是最外层文件夹：颜色点 + 序号（就是顺序，拖拽后重排）+ 标题 + 总负责人 + 状态徽标 + 进度；
- 任务可折叠；折叠时显示「几个部门 / 多少人 / 进度」；
- 任务内先显示**总负责人**（默认总控，也可以换人），再显示该任务下的**部门**（部门 = 这个任务里拉起来的团队，如研发部、市场部），部门可展开看成员；
- **未分派**只收没有任务归属的 Bot（旧数据、临时 Bot），默认折叠，不再混在任务区里；
- 「+ 新建任务」在任务区右上角；右键任务可重命名/改颜色/归档/删除。

### 工作台（一次只看一个任务）

```
工作台   [ 1 ● 发布会筹备 ▾ ]        ← 任务选择器（文件夹样式，带颜色/序号/状态）
         总负责人 总控 · 状态 进行中 · 截止 周五 · 预算 ¥500 · 3/4 子任务

   [看人]  [看事]          ← 只显示这个任务的人/树/产出
   ┌──────────────────────────────────────────────┐
   │ 总控（总负责人）                                │
   │   ├ 研发部 ─ 负责人 阿码 ─ 成员…                │
   │   ├ 市场部 ─ 负责人 小文 ─ 成员…                │
   │   └ 任务产出 / 验收 / 风险 / 需要你（只属于本任务）│
   └──────────────────────────────────────────────┘
```

规则：

- 顶部是**任务选择器**（不是部门选择器）：显示颜色/序号/标题/状态，可切换任务；
- 没有「全公司混合视图」；默认展示最近活跃的任务；从简报/对话点进来会带上对应任务；
- 没有任务时显示引导：「给总控一个任务，它会在这里生成一个任务文件夹」；
- 任务列表页（可选、很轻）不是工作台主视图：只有列表（任务、负责人、状态、进度、耗时、花费），点进去才进该任务的工作台。

## 二、数据模型

最小改动、向后兼容：

```ts
/** 任务文件夹：用户视角的最外层容器 */
interface TaskFolder {
  id: string;              // 自动任务用 dispatch run id；手动任务的生成 id
  title: string;           // 默认取总控计划的 goal / 用户给的任务名
  color: string;           // 复用 DEPARTMENT_COLORS
  order: number;           // 侧栏顺序，拖拽更新
  collapsed: boolean;      // 用户折叠状态
  leadBotId: string;       // 总负责人（默认主 Bot 总控）
  status: "draft" | "running" | "done" | "failed" | "archived";
  runId?: string;          // 关联的派单 run
  createdAt: number;
  archivedAt?: number;
}
```

- 部门增加 `taskId`：`OrgDepartment { ..., taskId: string }`；`(taskId, section)` 才是一个部门（同名部门可以在不同任务里各有一个）；
- Bot 增加 `taskId?: string`：成员归属任务；未设置 = 未分派；
- 领导关系：任务内部门的负责人仍用 `bot.chiefOfStaff` + `section` 表达，任务总负责人是 `leadBotId`；
- 一个 Bot 同一时间只属于一个任务（阶段 1）；跨任务协作通过「借调」后续再做；
- 所有排序/折叠状态存 sidecar 偏好文件（按用户本地），或直接在 TaskFolder 里存（单机应用，直接存即可）。

API 草案：

- `GET /api/task-folders` → 任务列表（含状态/进度/成员数）
- `POST /api/task-folders` → 新建（title/color/leadBotId）
- `PATCH /api/task-folders/:id` → 重命名/改色/排序/折叠/归档
- `DELETE /api/task-folders/:id` → 归档（不删 Bot）
- `GET /api/task-folders/:id/org` → 该任务的部门/成员/负责人/运行
- `POST /api/task-folders/:id/departments` → 在任务下创建部门

## 三、与现有模型的关系

| 现状 | 新模型 |
|---|---|
| `bot.section` 一个全局字符串 | `(taskId, section)`；旧数据迁到默认任务 |
| 全局 `org.departments` 数组 | 每个任务下自己的部门列表（底层仍是 section + lead） |
| 工作台 = 全公司楼层图 + 全公司树 | 工作台 = 当前任务的范围视图 |
| 侧栏 = 部门分组 | 侧栏 = 任务文件夹 → 总负责人 → 部门 → 成员 |
| 派单 run 独立存在 | 派单 run 自动创建/关联一个任务文件夹（run goal → title） |
| 部门颜色/编制/预算 | 任务内部门沿用这些配置；任务本身再有一层颜色/预算/截止 |

## 四、迁移

1. 启动时若没有 `task-folders.json`：创建一个默认任务文件夹「历史任务」（颜色取第一个，order 0），把所有现有部门/有 section 的 Bot 挂进去；
2. 无 section 的 Bot 保持「未分派」；
3. 旧链接/旧事件里的 section 继续可用（内部查询按默认任务解析）；
4. 之后的新任务全部创建独立文件夹；
5. 回滚：保留旧 sidecar 快照；任务式视图和数据迁移可分别开关（隐藏入口即可退回旧工作台）。

## 四·五、先做的第 0 步（已实现，降低「乱」的观感）

- 工作台不再把「未分部门」画成楼层里的一间房：`unassignedBots` 从 `rooms` 里移除；
- 工作台顶部出现一条细横幅「有 N 个 Bot 不在任何部门 · 整理」，点开弹窗可逐个「移入部门」或「打开聊天」；
- 侧栏里这个桶从「未分部门」改名为「**未分派**」，仍放在最后；
- 这样先解决「页面里到处是未分部门」的观感，再按阶段做任务文件夹，不会一次性推翻。

## 五·五、老板已确认的规则（2026-10-17）

1. **一个 Bot 同一时间只属于一个任务，这是硬规则。** 要并行第二个任务，就新建 Bot；不共享上下文、不串味。
2. **任务负责人 ↔ 总控之间要沟通协调。** 负责人向上报进度/风险/需要什么；总控管预算、加人、新建 Bot、跨任务调配。
3. **快的 Bot 要被重新派活。** 发现某个 Bot 很快完成，就分配部门里的其他任务，或去辅助进度较慢的任务；不能让它闲着。
4. 调配顺序：同部门待领 → 同任务其他部门待领 → 辅助同任务里慢的 → 都没有就待命（不跨任务借人）。
5. 重新派活必须留痕：由负责人/总控决定，写进任务时间线，Bot 对话里能看到「被调配」。

**实现进度（后端，已带测试）**：

- 「一个 Bot 只属于一个任务」已落到派单：分配时会跳过那些在别的进行中任务里还有 pending/running 子任务的 Bot；没有合适的人就新建专员（`assignedElsewhere`）；
- 「快的人重新派活」已落到派单：某个子任务成功后，空闲队友会接手**同一任务内**「主人正忙、尚未开始」的子任务（同部门优先，其次看角色匹配）；`reassignedFrom` 记录原负责人，工作台报告里显示「接手自 X」，任务时间线发一条「提前完成，接手了…」；
- 尚未做：跨任务借调（只能由总控决定：新建 Bot 或明确移交）。

## 五·六、2026-10-17 第二轮确认（任务权限 & 同部门互助）

1. **总控在所有任务之上**：总统筹全部任务，直接向老板汇报；任务完成后老板可以跟总控说，也可以直接进那个任务说。
2. **任务负责人 ≠ 总控**：新建任务后，任务下面负责该任务的是**该任务的总负责人**（有任务级权限），不是总控。总控是公司层，任务负责人是任务层——这是权限边界，不能混。
3. **同部门互助**：部门同事在同一任务里，如果任务负责人没有给该部门下新命令、且不需要数据独立，空闲同事可以主动辅助进度慢的同事（接手对方尚未开始的活）；不需要等负责人逐条下发。
4. **已完成任务暂不归档**：先留在任务列表里（老板已确认）。
5. 工作台继续按「任务内协调」方向做；调配顺序沿用原规则。

**实现进度**：同部门互助规则已落到派单后端（`rebalance(..., "helping")`：Bot 空闲时接手同部门忙同事的未开始子任务，任务时间线记「空闲，帮着 @某某 一起做」）；任务负责人权限模型（任务自主负责人、总控在上）进入阶段 3 的数据模型改造。

> 中途换模型的上下文交接设计见 [`docs/model-switch-handoff.md`](./model-switch-handoff.md)（不重放历史，用结构化交接包 + 切换前显示 token/费用估算）。

## 五·七、老板最终裁决：任务窗口与上下文共享（2026-10-18）

1. **新任务必须是新窗口**：每次开新任务 = 新对话页，不复用旧窗口。
2. **上下文可以分享，但只分享"经验"，不搬"聊天记录"**：如果新任务跟之前的员工有类似关系，可以给他分享之前任务的上下文；默认只给 Handoff 摘要（有界），不给旧对话全文。
3. **已完成的老任务窗口必须保留**：员工可以被释放、被后续任务复用，但**不能把员工调度进新任务**、不能动旧任务的窗口；旧任务的对话、产物、验收证据原样保留，供老板复盘。
4. 老板已授权：这类产品/实现决策由工程方与 Claude 评审自行决定，不再逐条请示。

**落地（已开始）**：
- `TaskFolder.conversationId`：任务自己的窗口（`run.sourceThreadId`），新任务新建、旧任务永不覆盖；已完成任务保留该窗口；
- 员工（Bot）与任务解耦：Bot 可以复用，但旧任务的会话属于旧任务；
- 上下文共享字段 `sharedFromTaskIds` 已建模，下一步接「只注入旧任务 Handoff 摘要」的注入逻辑。

## 六、开放问题（需要老板拍板）

1. **任务粒度**：给总控的「一次具体任务」= 一个任务文件夹，对吗？（建议：是；同一个大目标下的多次对话可以手动合并/新建子任务）
2. **一个 Bot 能否同时属于多个任务**？（建议阶段 1 只属于一个；需要共享时用「借调」，避免上下文串味）
3. **已完成的任务**默认折叠还是自动归档到「历史任务」区？（建议：完成后留在列表，7 天后折叠进历史）
4. **任务总负责人**：默认总控，还是允许指定某个部门负责人当任务总负责人？（建议：允许，默认总控）
5. 旧全局部门（研发部）保留为「历史任务」里的部门，还是拆开让用户手动搬？（建议：整体保留，不拆）


## 八、他山之石：参考了别人产品的哪些思路（不照搬）

看了老板发来的两张同类产品截图，值得学的是**信息组织方式**，不是视觉或功能清单。我们吸收这 6 点，并加上一念自己的特色：

| 别人做得好的 | 我们怎么用（结合一念特色） |
|---|---|
| 侧栏按「项目」分组，下面是带相对时间的会话（10 小时前 / 5 天前） | 任务文件夹里也显示：进度、最后更新时间、花费/tokens、消息数；任务本身有颜色/序号/折叠（别人没有序号和拖拽排序） |
| 会话顶部一条「项目 · tokens · 最后更新 · 消息数」的上下文条 | 任务头部上下文条：任务名 · 总负责人 · 状态 · 截止 · 预算 · 花费 · 最后更新 |
| 聊天里嵌一条「团队」条：成员、组建团队、打开运行报告 | 任务对话里放一条轻量「任务团队」条：总负责人 + 各部门负责人头像 + 状态；按钮「任务看板」「运行报告」。点击不跳走，侧栏选中任务后仍留在对话里 |
| 执行前「团队执行前确认」卡（正在调整方案 · 0 位成员 · 查看并配置） | **任务启动前确认卡**（一念特色）：展示 Charter（成功标准 / 不做的事 / 约束 / 预算 / 截止）、按部门分组的子任务、每条的**验收标准与验收人**、预估耗时与花费；按钮：开始执行 / 调整计划 / 取消。小任务自动跳过 |
| 团队图：阶段、完成/进行中/待领/阻塞、已运行时长、实时跟随、回看历史、成员卡显示「停在 #n」、依赖分层任务板（可立即领 / 第 2 层 / 第 3 层 / 收尾）、通讯侧栏 | 工作台加「任务看板」视图：按**就绪度分层**（可立即领 / 等待依赖 / 进行中 / 待验收 / 阻塞 / 收尾），卡片显示部门、验收人、验收标准、边界、模型；顶部状态条显示阶段/进度/耗时/花费；「跟随团队」与「回看历史」放到阶段 5。**不同点**：验收/边界/验收人是我们的结构化字段，卡片天然可验收；别人只有依赖和阻塞 |
| Composer 显示模型、上下文占用、当前文件夹 | 对话底部已有模型/文件夹；任务对话里补「本任务累计 tokens / 上下文占用」 |

**不照搬的**：
- 不做功能对等的克隆；保持一念的像素吉祥物、看人/看事双视图、公司层规则（预算/审批/部门编制）。
- 不把「团队视图」做成独立页面，而是**任务文件夹的第二层**——因为一念的核心是「任务 → 负责人 → 部门 → 成员」，别人是「项目 → 会话 → 团队」。
- 我们的差异化是**派单总库 + 验收闸门 + 运行报告 + 复盘**：别人的任务板只展示依赖和阻塞，我们的每张卡都带验收标准/验收人/边界，完成后自动进入复盘与自我迭代。

## 七、为什么这样能解决「乱」

- 任务是最外层，部门不会跨任务堆在一起；任务多的时候只是文件夹多，每个文件夹内部结构固定（负责人 → 部门 → 成员）；
- 工作台永远只有一个任务的范围，楼层图/树不会把不同任务的部门混排；
- 颜色 + 序号 + 折叠/排序 = 用户自己能把 20 个任务整理成看得懂的顺序，而不是系统按创建时间硬排；
- 与派单天然对齐：一个任务 = 一个 run（可含多个部门/子任务），完成状态、产出、验收、风险都在任务内闭环。
