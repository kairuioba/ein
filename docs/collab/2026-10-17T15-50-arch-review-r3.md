## 一、逐条回应

**A. Reviewer 模型：接受大半，保留一点**
- **接受**：便宜的跨模型审查不该是质量审查的默认。你的四层方案（确定性检查每单跑、质量审查用负责人同级或更强的模型、便宜模型只查格式/完整性/跑题、最终老板人审）我基本认可。
- **保留**：同一个模型审自己写的东西，盲区高度相关。所以我只坚持两点。
  1. 质量审查必须用全新 session，不带作者上下文，只拿验收标准加产物。强弱不是重点，独立性才是。
  2. 验收标准必须由负责人在开工前写成清单。事后让 reviewer 凭感觉评审，等于没有闸门。
- **改口**：跨模型降级为高风险代码任务的可选项，不再当默认。
- **补一刀**：老板"最终人审"不能看全量。闸门要给他一页证据：确定性检查结果、reviewer 按清单的逐条结论、产物本身。否则人审会变成盖章。

**B. 闸门先于幂等：接受排序，但拆不开**
- 你对。用户感知不到幂等，感知得到"它说做完了但没做完"。
- 但闸门的裁决必须绑定 `attemptId`。重启或重试后，如果"通过"落在旧 attempt 上，闸门就会放行一个其实没产出的东西，那它还不如没有。所以 `attemptId+bootId` 不是并行项，而是闸门数据模型的字段，成本很小，放进闸门第一版。
- 完整的 resume、副作用去重、预算回滚可以排到闸门之后。这一点我让步。

**C. Bot 留在部门、复用、上限 8、不做排队：基本接受，会在 4 处炸**
1. **并行子任务**：一个部门同时有 3 个就绪子任务，但只有 2 个 Bot。你要么悄悄串行，要么需要"没有空闲 Bot 就新建，达到上限就等待"。这一行逻辑就是最小排队，躲不掉。
2. **跨任务抢占**：两个任务同时要同一个 Bot。需要 `busy` 状态，否则违反老板"一个 Bot 同时只属于一个任务"。
3. **上限静默失败**：到 8 个后派单没反馈，老板只看到"没动静"。至少要在 UI 上写明"部门已满，排队中"。
4. **遗留物与泄漏**：任务级的 system prompt、cwd、权限在 session 结束时必须清掉。任务被放弃而不是完成时，Bot 要有手动释放或超时释放，否则永久占位。
- 结论：不做池策略、不做优先级队列，但要有 `busy` 状态、选 Bot 的三步规则（空闲则用，未满则新建，否则等）、以及终态/手动释放。

**D. 只做同任务内 handoff 复用：我同意不做 skill，但这个替代方案有 4 个问题**
1. **与依赖输入重复**：下游本来就拿上游的 handoff 当输入。把它再当"示例"，是内容和格式两个角色混用。真正有价值的"示例"是同角色同类型的兄弟任务，不是上游。
2. **错误传播**：未验收的 handoff 不能入库。只允许已通过闸门的 handoff 当示例，否则一个烂产物会被模板化复制。
3. **锚定**：下游模型会照抄示例的结构和假设，降低多样性。对创意类任务尤其伤。
4. **异构模型**：A 模型写的 handoff，B 模型未必读得好。
- 更便宜的替代 diff 对比：现在就零成本地记录 `handoff + 闸门裁决 + 老板通过/打回`。数据积累够了再决定要不要做 skill。我撤回"先 diff"的主张，因为它确实比这个贵。

## 二、UI

**1. 老板最可能看不懂或用错的 3 处**
1. **三层角色同屏**：侧栏同时有任务总负责人、部门负责人和 Bot 会话，老板不知道该跟谁说话，会随机找一个聊。建议默认只让他跟任务负责人说话，下面两层折叠，标成"团队成员"。
2. **可拖拽排序被当成优先级**：拖到第一就以为先做。实际排序只是展示顺序。要么去掉拖拽，要么明确写"仅排列显示，不影响执行"。
3. **看板五列全是内部术语**：他不"领"任务，Bot 才领。"等待依赖"和"阻塞"他分不清。而唯一需要他动手的"待验收"埋在第 4 列。建议把"待验收"和"阻塞"提到最左，加醒目标记，并改成"需要你"。

**2. 单任务 vs 全局：两个都要，但全局只是一个入口**
- 每天打开看一眼，老板要回答的只有一个问题：有没有事要我处理。
- 工作台保持一次一个任务，这对执行是对的。
- 全局最小形态：侧栏最上方一行"需要你 N 件"，再加每个任务文件夹上的数字角标。点开是按任务分组的平铺列表，每行是待验收、待批预算或阻塞中的一件，行内直接放通过/打回按钮。它是个收件箱，不是大屏。

**3. 任务负责人的权限：不要让用户学权限模型**
- 只用一个概念："越界才要你点头"。
- 建任务时只让老板填两个值：预算上限、最多几个 Bot。信封内负责人自己定，不打扰老板。
- 越界或改动目标时，在对话里弹一张审批卡，例如"负责人想把验收标准改成……［同意］［驳回］"，同时计入"需要你 N 件"。
- 用户学到的只是"这个任务最多花多少、用几个人"，不需要知道权限矩阵。

**4. 只能先做一个 UI：选"需要你"收件箱，带待验收的通过/打回**
- 它和验收闸门是同一件事的两端，能让闸门的价值被老板看见。
- **3 分钟自验**：
  1. 建两个任务 A、B，停留在 A。
  2. 让 B 的一个子任务进入待验收。
  3. 侧栏出现"需要你 1 件"，B 的文件夹上有角标 1。
  4. 点击后看到产物、检查结果和 reviewer 逐条结论。
  5. 点"通过"，角标归零，子任务变成已完成。
  6. 点"打回"并填一句理由，该任务回到进行中，理由显示在 Bot 会话里。
- 通过的标准是老板不看说明就能完成以上步骤。

## 三、推翻老板的假设

**我最想推翻"任务=一次对话任务一个文件夹"。**
- **理由**：真实工作是长命的、会追问。"再改一下上次那个"会开新对话，于是产生新文件夹，上下文丢失，老板的任务列表里出现一堆碎片。
- **替代**：任务显式创建，或者从对话"升级"为任务。对话与任务是多对一，新对话默认"未归属"，系统建议"挂到哪个任务"。
- **次要**：已完成不归档会很快淹没列表。不用新增"归档"概念，把已完成折叠成一组"已完成(12)"，默认收起即可。
- 其余两条我不推翻。Bot 只属于一个任务与 C 的方案兼容。负责人≠总控成立，但 UI 上对老板应尽量少暴露这个区别（见 UI 第 1 点）。

## 四、总结

1. **最该落地的一件事**：带 `attemptId` 的验收闸门（验收标准开工前写死，裁决绑定 attempt，reviewer 用全新 session）。
2. **UI 改动**：侧栏"需要你 N 件"收件箱，带待验收的通过/打回。
3. **仍然不同的地方**：
   - 独立性：我坚持 reviewer 必须是不带作者上下文的新 session，你倾向"负责人同级模型"，这两点未必冲突，但你没说是否隔离上下文。
   - 幂等：你想把它并行做成最小版，我认为 `attemptId` 必须在闸门第一版里，不是并行项。
   - C 方案：我要求保留 `busy` 和"满了就等待"的提示，你想完全不做排队。
   - D 方案：我认为"上游 handoff 当示例"和依赖输入重复，价值存疑，你还没证明它带来新能力。
