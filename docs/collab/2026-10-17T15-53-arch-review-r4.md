## 1. 验收闸门 v1

**数据模型**（只加字段，不改 `acceptance`）
```ts
type Criterion = { id: string; text: string; required: boolean;
  check?: { type: 'file_exists'|'non_empty'|'json_parse'|'regex'; path: string; pattern?: string } }
Subtask {
  acceptance?: string            // 旧字段，保留只读
  criteria?: Criterion[]         // 新字段
  gate?: { state: 'none'|'checking'|'reviewing'|'pass'|'fail'|'needs_human'; reworkCount: number }
}
normalizeCriteria(st) = st.criteria
  ?? (st.acceptance?.trim() ? [{id:'legacy-0', text:st.acceptance, required:true}] : [])
```
- 旧数据不迁移、不回写，读取时 normalize。
- 已终态的旧任务不追溯跑闸门。
- 没有 criteria 的新子任务：`gate.state='none'`，只跑确定性检查，不进收件箱，否则会刷屏。

**reviewer 何时跑、怎么跑**
- 触发点：worker 的 attempt 正常结束后，子任务进入 `reviewing`。这是 dispatch 流水线里的独立 turn，不要同步塞在 worker turn 里，否则重启时没法区分在跑 worker 还是在跑 reviewer。
- 顺序：先跑确定性检查（产物存在、非空、能解析、声明的 outputs 都在、无 error 标记）。有一项不过就直接 `fail`，不调用 LLM，省钱。
- 引擎：全新 session，只读工具，temperature 0。v1 用同模型加全新上下文。跨模型 reviewer 是 v1.1，先不做。
- 输入只有这几项：
  - 验收标准列表；
  - 任务一句话目标；
  - 产物清单（path/size/sha256）加正文，每个文件截断到 N KB；
  - 确定性检查结果。
- 明确不给 reviewer：worker 的对话、自评、推理。
- 任何必需标准对应的证据被截断，该条记 `unverifiable`。

**ReviewResult**
```ts
{ attemptId, reviewerSessionId, reviewerModel, artifactDigest,
  verdict: 'pass'|'fail'|'needs_human',
  criteria: { id, verdict:'pass'|'fail'|'unverifiable', evidence:string /*≤300字*/, ref?:{path,line?} }[],
  deterministic: { name, ok, detail }[],
  reason?: 'criteria_failed'|'unverifiable'|'reviewer_error'|'truncated',
  summary: string /*≤200字*/, createdAt }
```
裁决由代码聚合，不信 LLM 给的总 verdict：
- 只有全部 required 标准为 pass，且确定性检查全过，才是 pass。
- 任一 `unverifiable` 得 needs_human。
- pass 但 evidence 为空，降级为 `unverifiable`。
- JSON 解析失败重试 1 次，仍失败得 needs_human（reason=`reviewer_error`）。

**状态机**
```
running → reviewing → pass → done
                    → fail → (reworkCount<1) 新 attempt，带失败标准作反馈 → running
                           → (reworkCount≥1) needs_human
                    → needs_human → 收件箱
老板：approve → done（记录 override）
      reject+note → 新 attempt，reworkCount 重置为 0
      abandon → cancelled
```
- v1 不做自动换模型，fail 两次就升级给老板。换模型只走手动入口。
- 任何路径都不会自动 pass。

**收件项**
```ts
InboxItem { id /*=`${subtaskId}:${attemptId}:${kind}`，幂等*/,
  kind: 'review_escalation'|'failed_exhausted'|'signoff'|'question',
  taskId, subtaskId?, attemptId, reason: string,
  evidence: { summary, criteria: ReviewResult['criteria'], artifacts:{path,size}[], checks },
  createdAt, seenAt?, resolvedAt?,
  resolution?: { action:'approve'|'reject'|'abandon', note?, at } }
```
- 子任务 pass 就直接 done，不进收件箱。
- 任务内所有子任务 done 后，生成一条任务级 `signoff`。这就是老板的一页证据。

**4 条测试**
- Unit 1：`aggregateVerdict` 表驱动。覆盖 unverifiable→needs_human、空 evidence 降级、截断→needs_human、全 pass→pass，另加 legacy 字符串经 `normalizeCriteria` 得到 1 条、空串得到 0 条。
- Unit 2：`buildReviewInput` 的快照测试。worker 最终消息里埋一个哨兵字符串，断言它不出现在 reviewer prompt 里，并断言截断标记存在。
- Integration 1：stub reviewer 连续返回 fail。第一次 fail 产生新 attemptId 且带反馈，第二次 fail 后子任务变 `needs_human`，且恰好 1 条收件项（重复触发不重复创建）。
- Integration 2：产物为空文件。reviewer stub 的调用次数为 0，子任务 `fail`，反馈里有确定性检查的原因。

## 2. attemptId / bootId

**字段**
```ts
Store.bootId        // 进程启动时 uuid，写入 store 头 lastBootId
Subtask.currentAttemptId: string|null
Subtask.attempts: Attempt[]
Attempt { id, n, bootId, model, engine, sessionId, startedAt, endedAt?,
  status:'running'|'ended'|'superseded'|'interrupted',
  endReason?:'done'|'error'|'restart'|'manual_retry'|'model_switch'|'rework',
  artifactDigest?, review?: ReviewResult, late?: boolean }
```

**什么时候写**：唯一入口是 `startAttempt(st, {model, reason})`，先同步持久化再 spawn。流程是生成 id、旧的 running 置 `superseded` 并尽力 abort、设 `currentAttemptId`。rework、手动重试、换模型、重启后重新分发都走这个函数。

**过期结果的判定**：`applyAttemptEvent(st, attemptId, evt)` 是所有写入的唯一出口（流式 delta、完成、工具结果、reviewer 结果都经过它）。满足任一条件即过期：
```
st.currentAttemptId !== attemptId
|| attempt.status !== 'running'   (reviewer 事件则判 reviewing 对应的 attempt)
|| attempt.bootId !== store.bootId
```
过期结果不碰子任务，只在 attempt 上标 `late=true` 并记日志。

**重启 reconcile**
```
load():
  for st in all subtasks where st.status in ('running','reviewing'):
    cur = st.attempts.find(id == st.currentAttemptId)
    if cur: cur.status='interrupted'; cur.endReason='restart'; cur.endedAt=now
    st.interruptCount++
    if st.interruptCount >= 3:            // 防崩溃循环
        st.status='needs_human'; emit inbox(kind='failed_exhausted', reason='repeated restarts')
    else if st.status=='reviewing' && cur?.artifactDigest && artifactsExist(cur):
        st.status='awaiting_review'        // 产物还在，只重跑 reviewer，不重做 worker
    else:
        st.status='pending'; st.currentAttemptId=null
        st.note='Interrupted by a restart' // 保留旧文案，兼容现有 UI
  for bot in depts: if bot.lease && !isRunning(bot.lease.attemptId): release(bot)
  persist once; store.lastBootId = bootId
```
- 重启不消耗 `reworkCount`，只累加 `interruptCount`。
- load 要幂等：连续加载两次，第二次什么都不改。

**与手动重试、换模型共存**：它们只是 `startAttempt` 的不同 reason。手动重试会把 `reworkCount` 重置为 0，历史 attempts 保留。迟到的旧 attempt 完成事件一律走过期分支。

**3 条测试**
- Unit：先 `startAttempt(A)`，再 `startAttempt(B, reason:'model_switch')`，然后 A 的完成事件到达。断言子任务状态和产物不变，A 的 `late=true`。
- Integration 1：写入一个 running 加 leased bot 的 store 后 `load()`。断言子任务为 pending、attempt 为 interrupted、bot 已释放，且第二次 `load()` 无变化。
- Integration 2：A 运行中手动重试出 B，让 B 先完成、A 后完成（乱序）。最终只有 B 的结果落地，A 不覆盖。

## 3. "需要你" UI

**接口**
- `GET /api/inbox?status=open` 返回 `{ items: InboxItem[], counts: { needsYou: number, unseen: number, byTask: Record<taskId, number> } }`。
- `POST /api/inbox/:id/seen`：只写 `seenAt`。
- `POST /api/inbox/:id/resolve`，body `{ action:'approve'|'reject'|'abandon', note?, expectedAttemptId }`。
  - `expectedAttemptId` 与当前不符返回 409，"已有新进展，请刷新"。这防的是老板点了一个已经过期的按钮。
  - reject 必须有 note，否则 400。
- 实时更新：复用现有推送事件 `inbox.changed`，没有就先 5 秒轮询。

**计数口径**
- 算"需要你"（`needsYou`）：open 状态的 `review_escalation`、`failed_exhausted`、`signoff`、`question`。只有 resolve 才会让计数减少。
- 只算"看到"（`unseen`，用小红点）：未 `seen` 的 open 项。打开详情不改 `needsYou`，只清红点。
- 不算：自动重试中、rework 中、reviewer 自己 pass 的、bot 容量等待。容量等待只在部门卡片上显示"等待空闲 Bot（排队 n）"，不进收件箱。
- 任务角标等于 `byTask[taskId]`。
- 侧栏一行显示"需要你 N 件"，N 等于 `needsYou`，为 0 时不显示。

**3 分钟自验脚本（非技术用户）**
1. 新建任务，验收标准写"生成一份不超过 3 行的总结文件"，派给部门。
2. 看侧栏。运行中应显示"进行中"，"需要你"应为 0。
3. 任务完成后，侧栏出现"需要你 1 件"，点开能看到一页证据：每条标准的通过/未通过、产物文件名。
4. 点"打回"并写一句话。任务应重新开始，"需要你"回到 0。
5. 完成后再点"通过"，该条消失，任务进入"已完成"折叠组。
6. 中途关闭应用再打开。运行中的任务应显示"被重启中断，已重新排队"，不应出现重复结果。

## 最可能出问题的一条

1. 最可能出问题的是 **`applyAttemptEvent` 作为唯一写入出口**。
2. 现有 dispatch 里很可能有多处直接改 `subtask.status` 或写结果的回调。漏掉任何一处，过期结果就会悄悄覆盖新结果。
3. 这种漏洞不会报错，只会在重试或重启的乱序场景下偶发，测试很难复现。
4. 建议在 Commit 1 开头用 grep 列出所有写 subtask 状态的位置，全部改成走这个入口，再加一条"直接赋值就让 lint 或测试失败"的守卫。
5. 其次是 `reviewing` 状态在 reconcile 时的 bot 租约释放，但那个只会卡住，不会错写数据。
