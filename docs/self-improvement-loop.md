# 自我迭代闭环：设计草案（2026-10-17）

> 目标：让一念从「任务 → 结果 → 复盘 → 改进 → 验证 → 发布」形成闭环，逐步做到「越用越会派活、越用越稳」，最终让维护机器人基于真实失败模式提出并落地代码改进（人保留批准权）。
> 状态：**设计草案**。阶段 1 的字段与数据已具备（派单总库、验收人、运行记录）；阶段 2 起逐轮实现。

## 一、现有基础（已经能用的部分）

| 能力 | 现状 |
|---|---|
| 派单与自动提示词 | `submit_plan`：拆解、依赖、自动建专员、推荐模型、结构化计划（目标/边界/交付物/验收标准/验收人） |
| 运行数据 | `DispatchRun` / 子任务状态 / 耗时 / 花费 / 重试 / 结果；维护岗运行记录 |
| 发布与回退 | 双渠道（stable/dev）、滚动 `dev` 预发布、`backup/v<版本>` 源码标签、verify 硬门槛（测试不过不发布）、运行链接 |
| 维护机器人 | 在源码仓库里改、开 `fix/*` 分支、跑测试、推送/发版前需批准 |
| 安全与审计 | `docs/security-review-*.md`、审批/预算/部门规则、只推自己仓库 |

## 二、四层闭环

### 1. 任务评估层（先做，成本最低）

每次派单结束，自动生成一条**复盘记录**（不依赖模型判断也能记录硬事实）：

- 每个子任务：状态、重试次数、耗时、花费、模型/强度、是否触发审批、验收人；
- 汇总：总耗时、总花费、失败/返工子任务数、是否需要用户二次干预（插话、改模型、停止、重试）；
- 可选：让总控在汇总后追加三行「这次哪里不顺、下次怎么派」。

存储：`~/.ein/dispatch-retros.ndjson`（只追加），接口 `GET /api/dispatch/retros`；工作台/简报里显示最近几条。

**进度**：后端已实现（`fix/dispatch-retros` 分支：run 结束时写入硬事实记录，`GET /api/dispatch/retros?limit=20`），带测试；UI 展示待下一轮。

### 2. 经验层（派单总库 + 失败模式库）

- **派单总库**：把被验证过的计划模板（按任务类型：写作/代码/调研/上线）连同边界、验收标准、验收人一起沉淀；`submit_plan` 前检索相似任务，把模板作为参考注入规划提示词。
- **失败模式库**：从复盘里归并出可复用的模式，例如「计划缺验收标准」「员工提示词缺输入文件」「模型能力不匹配」「审批卡信息缺失」「长任务被中断」；每条模式对应一个提示词补丁或代码改进项。

### 3. 改进层（半自动）

1. 维护机器人每周（或手动触发）读取复盘与失败模式，输出「改进提案」清单（含证据、影响面、拟改动）；
2. 老板勾选要做的项 → 机器人开分支修 → 跑测试（verify 门槛）→ 发 dev → 老板在开发渠道验收 → 转正式版；
3. 每次改进记录「改进前后指标」（成功率/返工率/平均耗时/花费），无效的改进可回退（backup 标签/旧 dev 安装包）。

### 4. 护栏（不可省）

- 测试是硬门槛；发布/推送必须老板批准；预算上限；只动自己仓库；永不强推 main；
- 自我修改的代码必须过安全审查清单（凭据、权限、发布链路、外部命令）；
- 任何「自动优化」默认只发 dev 渠道，正式版永远要人点头；
- 指标回退即回滚。

## 三、分阶段落地

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| 1（下一步） | 复盘记录 + `GET /api/dispatch/retros` + 工作台展示最近复盘 | 跑一次真实派单后能看到结构化复盘 |
| 2 | 验收闸门：员工交结果后，由 `reviewer`（Bot 或用户）按验收标准判 pass/fail，不过退回重做或换模型，过了才进汇总 | 验收标准真正约束交付；失败可自动重试 |
| 3 | 派单总库检索 + 模板注入；失败模式归并进规划提示词 | 同类任务的计划质量（含边界/验收）稳定提升 |
| 4 | 维护机器人按失败模式提案 → dev → 人验收 → 转正 的半自动代码改进 | 至少一轮「发现问题→自动修复→人工验收」闭环 |

## 四、关键判断

- 「自我迭代」不等于「无监督改自己」：**评估要可度量、改动要可回滚、发布要人批准**，否则会把偶发当规律。
- 先做 **阶段 1 + 2**：复盘和验收闸门直接提升派单质量，风险低；阶段 3/4 再谈自动化改代码。
- 评估指标建议：任务成功率、子任务返工率、验收一次通过率、用户干预次数、平均耗时/花费。
